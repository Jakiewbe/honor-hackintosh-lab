# R1.3-A｜Intel Iris Xe 8086:46A6：内屏输出双路线源码核验与技术决策

**2026-10-12｜结论：新方向有代码依据；两条路线均未达到实机/内核安全准入。**

`SOURCE_EVIDENCE_PINNED / NMXGPU_DIRECT_SCANOUT_CANDIDATE / NMINTELFB_FIRMWARE_DEPENDENT / RUNTIME_NO_GO`

## 0. 硬件档案和目标（不再重复确认）

用户已经确认 **HONOR GLO-FX6P 的内屏当前在 Windows 连接 Intel Iris Xe `8086:46A6`**；NVIDIA RTX 2050 Laptop PCI `10DE:25A9` 负责独显渲染。此前用户还报告 USB-C→DP 1080p/200 Hz 外屏正常，但其扫描输出 GPU 未确认。**不要再次索取内屏“连接到”截图**。

项目目标不是“某个模块编译成功”，而是确保 **macOS 图形→Intel 内屏的完整可用链路**。现阶段所有实机安装、kext 加载、Windows EFI/BIOS/磁盘修改均保持 NO-GO。

## 2. 路线 A：`NMIntelFB` + NVIDIA head 4（旧路线）

[固定源码 NMIntelFB/intelfb.cpp](https://github.com/nullmoth/nvidia-macos-driver/blob/1083a98db33a0bb824290556de255f9a95ca5403/kexts/NMIntelFB/intelfb.cpp) 和 [display_ids.inc](https://github.com/nullmoth/nvidia-macos-driver/blob/1083a98db33a0bb824290556de255f9a95ca5403/kexts/NMIntelFB/display_ids.inc) 显示：

1. `display_ids.inc` 包括 `{0x46a6, 13}`，说明源码**认识该 PCI ID / display version 13**，不是该 GPU 的 macOS 运行证据。
2. 实体模式 `adoptFirmwareMode()` **只寻找固件已经使能的 transcoder 和 plane**；若没有扫描中的 pipe，则明确失败退出。它还只接受 **linear XRGB8888** 的现有扫描平面；tiled 或不同格式直接拒绝。**该类的当前实现不会主动完成 Intel i915 的完整初始化、模式设置或恢复已经熄灭的面板。**
3. 成功映射旧平面后，`IOFBDependentIndex=4` 接给 NVIDIA `NVAccel`。通过 `NVRM_VRAM_FN_SCANOUT` 向 NVAccel 提供 **Intel 扫描表面的 CPU KVA**，设置 `phys = 0`，使 NVIDIA 画面经 CPU copy 路径送到 Intel 侧缓冲区，而不是直接将 NVIDIA VRAM 扫描到 Intel 面板。
4. `nvrm-accel.cpp` 对非 NVIDIA framebuffer 禁止 NVIDIA 专有 zero-copy flip；本项目的跨 GPU 方案仍受完整 NVAccel、共享缓冲区可写性、VBL 与资源生命周期约束。
5. 我们的 R1.2-C `real/virtual` BUILD-PASS **没有验证固件是否在 macOS 接管时保留线性 XRGB8888 plane**，也没有 NVAccel 的完整可复现本机构建、更没有 HONOR 内屏画面。

**风险判断：** “固件仍保留可用扫描平面”是条件性前提，不是已验证能力；不能凭 ABI/PCI ID 匹配决定恢复 NMIntelFB 内核补丁。**路线 A：NO-GO（保留为研究候选）。**

## 3. 路线 B：`NMXGPU` 的 Intel i915 → DRM → IOFramebuffer（新主研究方向）

[固定源码 nmx_kext.cpp](https://github.com/nullmoth/nvidia-macos-driver/blob/1083a98db33a0bb824290556de255f9a95ca5403/gpu-port/xkpi/xnu/nmx_kext.cpp)、
[nmx_fb_bridge.c](https://github.com/nullmoth/nvidia-macos-driver/blob/1083a98db33a0bb824290556de255f9a95ca5403/gpu-port/xkpi/override/src/nmx_fb_bridge.c)、
[nmx_fb.cpp](https://github.com/nullmoth/nvidia-macos-driver/blob/1083a98db33a0bb824290556de255f9a95ca5403/gpu-port/xkpi/xnu/nmx_fb.cpp) 显示：

```text
Intel 8086:46A6 ──> NMXGPU service (opt-in)
                             |
                             v
                     ported Linux i915
                       DRM mode setting
                             |
                     nmx_fb_bridge.c
               connected outputs + XRGB8888 buffer
                             |
                     NMXGPUFB (IOFramebuffer)
                             |
                  macOS WindowServer / internal panel

  Optional later: Intel ANV + NMXAccel/Metal (separate validation gate)
```

- `NMXGPU::probe` 以 vendor `8086` 和**显式 opt-in** 为前置，而不是一个自动承诺 `46A6` 已经初始化。注意激活 NMXGPU 涉及重新初始化拥有启动画面的显卡，**不得在主力机尝试**。
- `nmx_fb_bridge.c` 使用 DRM client 查找输出、选择模式、分配 XRGB8888 显示 buffer、`drm_client_modeset_commit` 再发布 `IOFramebuffer`。这是一条与旧 NMIntelFB “仅采用已有固件 plane”**功能范围不同**的源码路径；它至少企图驱动 display engine。
- 桥接要求其扫描 buffer 的 **CPU view 逐页连续的物理映射**（`nmx_xnu_kva_to_phys` 一页一页检查），如果映射不连续则失败。尚未证明 Intel Xe `46A6` 的真实 GGTT/stolen memory/host physical 布局符合此约束。
- 文档明确：仅实现最基本单 buffer / 单模式与镜像输出；模式切换、每个连接器的独立 framebuffer 等尚未完成。对日常笔记本休眠、亮度、热插拔与多显示器体验不能据此作保证。
- `NMXAccel`/Intel `ANV` 是单独层次：创建 Metal 设备不等于 DRM bridge 已接管 eDP 并稳定显示桌面。

### P0：新代码存在尚未关闭的生命周期隐患

在发布版本 `nmx_fb.cpp` 中直接可见：

- `vblFire` 在原始 `thread_call` action 中直接调用可变槽里的 `me->fVbl.proc(me->fVbl.target, me->fVbl.ref)`，未见对应回调槽生命周期同步或临时 target/owner 固定。
- `unregisterInterrupt(void *)` **直接返回 `kIOReturnSuccess`，不清理 `fVbl` 或 `fConnect`**；`setInterruptState` 也直接返回成功，不改变 enabled 状态。这无法从源码证明 IOGraphics 注销/禁用后 callback 绝不会继续到达。
- `stop()` 将 `fStopping` 设为 `volatile bool`，取消 timer 并反复 `thread_call_free`、`IOSleep(5)`；`volatile` 本身不构成跨线程引用、原子性和停止协议证明，仍需校验自等待、对象释放及同步 `terminate`。
- `nmx_fb_unpublish` 会调用 `terminate(kIOServiceSynchronous)`；`NMXGPU::stop` 同时管理设备 detach，这更要求 callbacks 和共享 scanout buffer 释放具有真实的同步排空保证。

这些是**源码上可审计的缺口/条件性风险**，不是我们在实机观察到死锁/UAF。不能简单移植 R1.2-C 补丁：`NMXGPUFB` 使用的 timer、owner 与 DRM 资源责任链都不同。

**路线 B：作为研究优先级更高，但作为实际安装仍然 NO-GO。**

## 4. 与其他“Xe 加速”项目的区别

2026-10-10 的 [r/hackintosh 初期公开报告](https://www.reddit.com/r/hackintosh/comments/1x26ygh/tiger_lake_alder_laken_xe_igpu_acceleration/) 自称 Tiger Lake、Alder Lake-N 在 **macOS Big Sur** 部分配置已完成 Metal/HDMI/DP 验证，但原贴明确说 **Alder Lake-P、笔记本和 USB-C 输出尚未验证/支持**。不能把 `N100` 等 Alder Lake-N 与本机 `i5-12500H/46A6` 混为一谈；社区自报也不能替代日志、源码与独立复现。

Intel 官方对 `46A6` 的 i915 支持限定为 **Linux 驱动支持证据**，不覆盖 macOS 引导、驱动映射、显示、Metal 或重启恢复。

### 本轮正式决策

1. **冻结** R1.2-C～G 的 VBL Patch Loop；已有模型留存历史证据。
2. **首要研究分支改为 NMXGPU Intel i915 DRM→IOFramebuffer 的实机可行性和生命周期阻塞审查**，先寻找**外部非主力环境**证据。此前确认的 Intel 内屏事实作为固定前提。
3. **次要分支保留 NMIntelFB / NVIDIA→Intel CPU copy**，但仅在 upstream 能证明固件扫描平面保留、`25A9` Metal 和完整复制输出后恢复。
4. 若两条路线都不能取得可信的 macOS 真实显示输出证据，则项目停在源码研究，不在主力荣耀安装 macOS。
