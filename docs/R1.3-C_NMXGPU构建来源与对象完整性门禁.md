## 2. 上游 i915 构建链路：关键依赖尚不能闭合

```text
           [外部 drm-kmod，实际 Git SHA 未确定]
                         |
   gen_flags.py <-------+---- kconfig.mk
         |              |
      amd.flags --------+---- i915/Makefile
         |                    |
         v                    v
     srclist.py -------> srcs-i915.all --[EXCLUDE + fork/override]--> srcs-i915.txt
                                                                          |
[外部 FreeBSD LinuxKPI / headers，SHA 未确定] -- cc-i915.sh <-----------+
                                                  |
                                               obj-i915/*.o
                                                  |
[外部 FreeBSD runtime, Linux 6.14 xe, DRM & XNU glue] ---> kext/build.sh
                                                               |
                                                          NMXGPU.kext

  以上是源码层面的构建设计，并非已获得的发布物构建记录。
```

`cc-i915.sh` 中 `LINUXKPI_VERSION=61400` 是**编译宏的版本设定**，不是对外部源文件 Git SHA 的证明。上游 `gpu-port/README.md` 中 900 / 274 / 193 / 75 个源文件数量只是上游的构建描述；本项目没有拿到生成的 `srcs-i915.txt`、`amd.flags`、`obj-i915/*.o` 逐文件 SHA 列表、链接映射或对应 Xcode 工具链标识。

## 3. 本轮新增发现：构建脚本可能出现“并非所有 i915 源码成功编译，但后续仍继续”的情况

**P0-NEW-A：源清单缺失提示被屏蔽。** `srclist.py` 对未能找到的 Makefile `SRCS` 输出 `#MISSING` 到 **stderr** 并 `continue`，但调用者 `all-i915.sh` 使用：

```sh
/opt/homebrew/bin/python3 srclist.py "$K/drm-kmod" amd.flags i915 2>/dev/null > srcs-i915.all
```

因此缺失源文件的诊断不会正常出现在该步骤的终端输出中，而缺失文件也不会进入 `srcs-i915.all`。静态确认**存在漏列时无法明确报错的路径**；不是声称上游发布构建实际发生了漏列。

**P0-NEW-B：汇总失败而不强制失败。** `all-i915.sh` 对每个 i915 编译失败写 `logs-i915/<object>.failed`，计算 `bad` 并打印：

```sh
echo "sources: $n  compiled: $((n - bad))  failed: $bad"
```

但没有 `[ "$bad" -eq 0 ] || exit ...` 或等效的显式失败门禁，也没有在源清单生成失败时对其计数和对象名逐个核验。因此其最后的诊断管道一般可正常结束，并不能凭 shell 退出码证明 `bad=0`。

**P0-NEW-C：对象目录不保证本轮纯净、缺少对象清单闭合。** `all-i915.sh` 只清除 `logs-i915/*.log` / `*.failed`，**没有清除 `obj-i915/*.o`**；而 `kext/build.sh` 使用 `obj-i915/*.o` glob 链接，不对照 `srcs-i915.txt` 的对象基名作集合相等校验。旧对象是否真的混入特定上游发布包**未知**；但从代码看，构建设计本身**缺少“清洁输入 + 全对象属于本次编译”的证据**。

**正确判断**：即使某次 `NMXGPU.kext` 链接成功，也不足以单独确认“所有 274 项 i915 源文件均参与并来自固定源头”。反过来，这三个缺口**也不证明发布的 NMXGPU 二进制必然不完整**；必须取得实际构建清单并在隔离环境中验证。

## 4. 上游其实展示了完整编译来源归档的技术办法，但用于另一个组件

[NullMoth v1.14.2 GitHub Release](https://github.com/nullmoth/nvidia-macos-driver/releases/tag/v1.14.2) 列出的附属资产为：

| 资产 | 公开记录中的体积 | 能说明什么 |
|---|---:|---|
| `nmxnpu-source-1.14.2.tar.gz` | 1,647,148 B | **单独的 NMXNPU 完整对应源码归档**，不是 NMXGPU |
| `nullmoth-nvidia-1.14.2.tar.gz` | 371,689,122 B | 软件包；其内部未在本轮展开逐项审计，不能断言包含或不包含 GPU 编译输入 |
| `1401-Mac-1.14.2.dmg` / `.zip` | 3,042,457 B / 2,657,066 B | 应用程序分发包，不是 i915 对象构建映射 |
| `SHA256SUMS.txt` | 362 B | 发布资产完整性入口；哈希不等于构建来源可复现 |

`kext-npu/mksource.sh` 专门对 NMXNPU 编译时用 `-MD` 收集源文件和编译器实际读取的头文件，并将外部 Linux、drm-kmod、FreeBSD 路径拷贝进归档。**这证明上游有一条能收集编译依赖的流程**；然而本轮审查 `gpu-port/xkpi/kext/` 仅包含 `Info.plist` 和 `build.sh`，没有发现等价的 NMXGPU `mksource`，发布资产中也没有以 NMXGPU 为名的完整对应源码归档。

重要限定：上述是**公开仓库与发行资产索引的证据缺口**，不是宣称 `nullmoth-nvidia-1.14.2.tar.gz` 的内部没有任何源码；它在本轮未下载、执行或解包，也未检查上游开发机器的私有构建目录。

## 5. 真正能让构建门禁从 BLOCKED 提升的最低证据包

后续应优先争取以下**机器可核查的文本/哈希证据**，而不是新的整套自动化、模拟测试或 VBL 补丁：

| 证据 | 验收条件 | 缺失时判断 |
|---|---|---|
| `drm-kmod` / `freebsd-src` / Linux 源树来源 | repo URL + 精确 40 位 commit + 补丁/本地修改差异，或编译输入逐文件 SHA-256 | **PROVENANCE BLOCKED** |
| `amd.flags`、`srcs-i915.all/txt` | 完整内容与 SHA-256，`#MISSING` 列表显式为空 | **SOURCE SELECTION UNVERIFIED** |
| 本轮每个编译对象的记录 | 每个源码路径 → object 路径 → SHA-256，`bad == 0`，没有旧 `.o`；`obj-i915` 集合与预期清单一致 | **OBJECT COMPLETENESS UNVERIFIED** |
| 链接与依赖证据 | xcrun/SDK/Xcode 版本、完整链接参数、`NMXGPU` 二进制 SHA-256、符号/映射或可审计链接记录 | **BINARY CORRESPONDENCE UNVERIFIED** |
| 设备路径验证 | 确认 `46A6` 的 PCI/Display ID 表在**真实构建输入中**，以及 i915 probe/eDP/GGTT 关键对象有编译/链接记录 | **DEVICE SUPPORT IN RELEASE UNVERIFIED** |

**即使整个构建证据包满足，最多升级为 `BUILD_PROVENANCE_VERIFIED`，仍非 `DRIVER_RUNTIME_GO`。** 下一项 P0 仍是 R1.3-B 已定义的 buffer backing（GEM/TTM→`vmap`→`pmap_find_phys`→`IODeviceMemory`）、eDP modeset 与生命周期证明。

## 6. 避免无用功的后续决策

1. **暂停**对同一上游版本的重复编译、同类静态测试和 VBL Patch Loop；先取得构建完整性证据。
2. **不立即创建新的 GitHub Actions**：当缺少上游实际源码/对象清单时，换一台 CI runner 重编一个独立候选树不能证明已发布的 NMXGPU 含有相同对象。
3. 可供将来向上游开发者核实的具体问题是：是否能提供 v1.14.2 对应的 `drm-kmod/freebsd-src` Git SHA、`amd.flags`、`srcs-i915.txt`、全部 i915 对象 SHA/失败记录和最终链接 map？本轮**没有替用户公开发布 Issue 或发送消息**。
4. 若上游不能提供可复核的来源，应保持 `BUILD_PROVENANCE_BLOCKED`；不在主力 Windows 机器上测试内核驱动。只有来源闭合且有隔离实机显示证据，才讨论进一步修复和安装准入。
