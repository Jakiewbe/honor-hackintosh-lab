# R0.9 — Static NMIntelFB kernel extension package audit

## Evidence so far

R0.8 `link` workflow [run 38197014657](https://github.com/Jakiewbe/honor-hackintosh-lab/actions/runs/38197014657) **succeeded** on an Intel macOS 15 runner. The real upstream `intelfb.cpp` translation unit compiled, and the linker reported `Mach-O 64-bit kext bundle x86_64`.

The linker emitted four deployment mismatch warnings: SDK libkmod archives built for macOS 15.5, with the link target defaulting to 15.0. The R0.9 pipeline explicitly sets `-mmacosx-version-min=15.5` for both compiler and linker. This is a build configuration correction, not a driver function fix.

At NullMoth pinned commit `0960b2ef5dbc4a573056d4c8e042a5bd2e15d651`, `kexts/NMIntelFB/display_ids.inc` includes the exact Intel iGPU device `0x46a6` with internal display version `13`, blob SHA `03fc18f018be25593fd60966799822e5f5d97b1e`. `Info.plist` includes an Intel-vendor PCI match and display-class match. This proves **static inclusion**, not firmware compatibility or functional display acceleration.

## R0.9 checks

Manual workflow [HONOR R0.9 Intel kext package inspection](https://github.com/Jakiewbe/honor-hackintosh-lab/actions/workflows/intelfb-package-audit.yml):

1. Pin and integrity-check the original NullMoth source.
2. Compile the unmodified `intelfb.cpp` with the macOS kernel SDK for x86_64 and explicit macOS 15.5 minimum deployment version.
3. Link a temporary unsigned `NMIntelFB.kext/Contents/MacOS/NMIntelFB`, and copy the pinned upstream Info.plist to `Contents/Info.plist`.
4. Verify the kext bundle identity and internal Intel `8086:46A6` table entry, inspect Mach-O header and imported symbol names.
5. Retain **diagnostic text files only**, not the object or binary. The runner deletes its temporary files at the end.

**Run manually:** Actions → HONOR R0.9 Intel kext package inspection → Run workflow → main.

## Safety, remaining gaps, and stop criteria

The workflow does **not** attempt kernel collection dependency resolution, signing, notary approval, load testing, GPU initialization, firmware scanout takeover, OpenCore injection, disk modification, or EFI/BIOS changes. Success is **not** evidence of macOS Metal support on Ampere RTX 2050.

A static build can never establish these properties of HONOR GLO-FX6P:
- Whether firmware leaves the Intel plane scanning out **linear XRGB8888** at boot;
- Actual GPU display routing and MMIO/BAR/GGTT state;
- Lifetime, locking, callback completion and framebuffer safety on real machine;
- Support for Ampere RTX 2050 as a working Metal accelerator.

The project should **not** interpret more green CI runs as an increasing likelihood of fully working GPU acceleration. After R0.9, prioritize code and safety audit plus independent hardware feasibility evidence; do not request changes to the user's primary Windows device.
