## 1. 审计证据等级

**A｜源码确定事实**：能在固定版本文件的明确行号直接证明。
**B｜条件性风险**：给出可能发生的前提，尚无硬件复现。
**C｜硬件未知**：编译、链接、设备 ID 表匹配都不能回答。

本轮所有“问题”均在 A/B 层；**没有**声称观察到真实内核越界、死机、Metal 渲染、内屏亮屏。R0.9 的 CI 成功不能提高硬件运行成功率的证据等级。

### 主动确认的已有防线

1. `NMIntelFB::adoptFirmwareMode()` 对 BAR2 扫描面已使用 **64 位加法和乘法**校验 `fSurf + pitch * height <= fApertureLen`，不是完全没有边界检查；R10-03 专指 **BAR0 寄存器映射长度**，二者不同。
2. `NVDisplayPipe::performTransaction` 对来自 NVIDIA 资源的来源尺寸与 `vm->fBytes` 有部分比较；对 IOSurface 亦有部分范围检查。但**目标 q 的实际映射容量契约仍不完整**，不能用局部检查替代全链路证明。
3. `NVRMFB` 原生 NVIDIA 帧缓冲生产者已经填写 `actualSize`，说明 ABI 存在**无需修改结构布局**的容量字段可供统一使用。
4. 静态 PCI 设备表包含 `0x46a6` (display version 13)；仅意味着 `probe` 有匹配分支，不意味着内屏可接管。

## 3. 关键修复合同（审查意见，不是已合并补丁）

### A. 统一扫描面容量合同

- 生产者：`NVRM_VRAM_FN_SCANOUT` 返回 `kva, width, height, pitch, actualSize`。容量应是**实际映射可写的字节数**，且映射本身有可验证的生命周期。
- `NMIntelFB`：获取 `fSurfMap->getLength()` 并确认 `fSurfMap->getVirtualAddress()` 有效、行跨度大于等于 `4*width`、`actualSize` 足以覆盖最后一行；不满足则返回错误，绝不能返回可用指针但容量 0。
- 消费者：任何复制操作均需要**源、目标两端的容量**；转换成无溢出判断 `row_bytes <= capacity` 和 `(rows-1) <= (capacity-row_bytes)/pitch`，不要先计算可能溢出的乘积。验证 `pitch >= row_bytes`、像素格式、非零尺寸、映射生命周期。
- 当前 `NVRMFB` 与 `NMIntelFB` 需同时纳入新合同的兼容性测试，避免仅为 Intel 端加限制反而破坏既有 NVIDIA 端。

### B. BAR0 寄存器边界

- `rd()` 的调用序列遍历 `p = 0..3`；寄存器中最大偏移是 `PLANE_SURF(3)=0x7319C`，32-bit 读取要求映射大小**至少 `0x731A0` 字节**。
- 在首个 `rd` 前验证 `fMMIO != nullptr`、`fMMIO->getVirtualAddress()!=0`、`fMMIO->getLength()>=0x731A0`；对 `getDeviceMemoryWithRegister(BAR2)` 的 aperture base/length 单独保留现有检查。
- 检查失败应拒绝接管并释放本驱动资源；不进行寄存器盲读或假设“同系列 Intel 芯片 BAR 尺寸都一样”。

### C. VBL 和 NVAccel 异步事务

- `volatile` 不等于线程间同步；stop / unregister / callback / 重排队需要建立单一可证明的状态机。
- `unregisterInterrupt` 不能仅报告成功；必须阻止旧目标回调在对象释放后继续被调用。
- (gIopAsync=1) 为源码默认值，但 `gNvIop=0` 也是默认值。讨论异步问题必须同时记录两个总开关的真实状态。
- 在内核实际加载与并发模型经第三方审查前，维持“不同步装/不加载”的项目准入。
