## Limit of conclusion

**R0.9 achieved native compile, link, and static bundle-format qualification — NOT real-world loadability or framebuffer functionality.**

Intel device ID presence is only a table match. macOS has no ordinary native Intel Iris Xe Alder Lake graphics acceleration; the NMIntelFB code proposes taking over an existing Intel firmware scanout. The NVIDIA RTX 2050/Metal path remains independent and unverified. This CI environment contains neither GPU.

In particular, we have **not proven**:
1. Whether the macOS boot firmware path leaves a lit Intel panel in a compatible mode on HONOR GLO-FX6P.
2. Whether the real plane is **linear XRGB8888** rather than tiled/compressed.
3. Whether Intel BAR0/BAR2, GGTT offsets and scanout mappings satisfy all range/lifetime assumptions.
4. Whether window-server framebuffer binding, virtual blanking, teardown and concurrent CPU-copy paths are safe.
5. Whether OSBundleLibraries, linkage/imports and macOS kernel collection policies allow actual loading.
6. Whether the RTX 2050 Ampere NVIDIA RM / NVAccel / Metal backend is functional.

## Pinned source gates for R1.0

The source in `kexts/NMIntelFB/intelfb.cpp` gives an explicit pass/fail path:
- `probe()` maps PCI device ID via `display_ids.inc`; 0x46a6 is listed at display version 13.
- `adoptFirmwareMode()` only accepts an **enabled transcoder and primary plane**, `fmtOf(PLANE_CTL) == 8` (XRGB8888), `tileOf(PLANE_CTL) == 0` (linear), valid width/height/stride and sufficient BAR2 aperture. Other layouts return false.
- `start()` uses PCI BAR0 register mapping and BAR2 aperture, then maps `fApertureBase+fSurf`; absence or mismatch stops the takeover path.
- `callPlatformFunction(NVRM_VRAM_FN_SCANOUT)` hands NVAccel a CPU `kva`, width/height/pitch and `phys=0`. The **request structure's buffer size/capacity contract must be audited** before treating this as safe NVIDIA-to-Intel frame copy.
- The driver uses timer-based VBL callbacks. Real stop/teardown and callback ownership safety are not established by CI.

These are properties of the original source, **not observed hardware facts**.

## Decision (STOP/GO)

**GO:** continue original-source audit, fail-closed display/VRAM bounds analysis, static symbolic import classification, and research into fully reproducible NVIDIA Darwin build inputs and credible Ampere physical tests.

**NO GO:** no primary-laptop EFI/BIOS/partition changes; no kext load or signing experiments; no claiming that the screen, OpenCore, Metal, RTX2050 or Intel graphics acceleration work.

**Avoid repetitive CI churn.** Further green builds would mostly reconfirm what R0.9 already establishes. Advance to an experiment only when it answers a specific missing hardware or runtime compatibility question with clear rollback boundaries. The user has not committed an independent Mac or disposable hardware test platform.
