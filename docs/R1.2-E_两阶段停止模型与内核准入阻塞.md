## 2. 为什么不能只在 stop 中「标记然后返回」

`IOFramebuffer::stop()` 具有内核服务生命周期含义。若 `NMIntelFB::stop` 从 VBL 回调内被同步触发，简单地设一个 `deferStop=true`、随后对系统返回成功，将使调用者相信停止已完成，而实际上 timer、PCI/内存映射和监听者仍可能被使用。

在没有验证过 `IOService::stop` 能被合法重定向或延迟、并且不能控制外部监听者如何再入的条件下，这种实现不可接受。我们不能为避免死锁而制造虚假的停止完成信号。

## 3. 两阶段协议参考模型（**不是可编译 kext**）

[源码 `tests/test_r12e_quiesce_finalize_model.py`](../tests/test_r12e_quiesce_finalize_model.py) 采用以下状态：

| 状态 | 解释 | 允许行为 |
|---|---|---|
| `ACTIVE` | 正常启动，无停止请求 | 在 FB gate 内读取/固定监听者、进行 VBL |
| `QUIESCING` | 收到停止请求，尚有 VBL action 栈 | 禁止 rearm；清空新 callback 槽，仅**延迟**外部 target 最终释放 |
| `DRAINED` | 所有已模型化的回调栈退出 FB gate | 在合适的 gate 外部回收目标引用，准备 Finalize |
| `FINALIZED` | 假设存在独立可靠的外部停止执行器，且完成标准 SYS→FB 清理 | 禁止新的回调，重复 finalization 不再执行 |

状态约束：

- **允许回调请求 quiesce，不允许在仍持有 FB gate 的回调栈内同步执行完整 `IOFramebuffer::stop`**。模型对未经证明的真实同步停止入口明确返回 `BLOCKED_UNPROVEN_SYNC_IOKIT_STOP`，绝不伪报成功。
- `unregister` 在 gate 内只转移监听者槽所有权，不立即调用有潜在副作用的最后一个 `release()`；必须在 callback 完成、门锁退出后以单独安全执行者完成退休目标的释放。
- 同时出现停止与注销时，避免双重最终释放；只有 `DRAINED`、无进行中回调和无待释放对象，才允许抽象的 `finalize_external`。
- 如果没有进行中回调，`quiesce_request` 可以立即进入 `DRAINED`；这一条在最初模型测试中曾失败，修正后重新执行。
- 离线纯 Python 环境实测：**12/12 单元测试通过；深度 8 状态枚举达到 113 个不同状态**。这些性质依赖“可靠外部执行器”这一**尚未证实**的假设。

## 4. 对现有 R1.2-C 源码的失败即停止扫描

[审查用 `scripts/r12e_stop_source_gate.py`](../scripts/r12e_stop_source_gate.py) 指向**三层补丁叠加后的临时源码目录**。它只检查已知风险的具体源码形态并始终输出 `NO_GO`，不会因某一字符串消失便自动升级到 `GO`。可选 `--enforce-go` 在仍有阻塞时用退出码 2 阻断部署自动化。

已知仍需要人工消除的风险包括：

1. VBL 在控制器 FB gate 内执行外部 `snapshot.proc`，该目标可以通过同步控制流触发 `stop` 或 `terminate`。
2. `registerGate`、`unregisterGate` 在 FB gate 内释放旧监听者，可能触发非预期的析构再入。
3. 回调内 `snapshot.target->release` 同样可能落在 FB gate 内，虽然 R1.2-C 的 owner/sender pin 降低了部分 UAF 风险。
4. `NMIntelFB::stop` 最后直接调用 `IOFramebuffer::stop(provider)`；没有证明它一定在符合 SYS→FB 的上下文中进入。

此扫描器仅提供显式 NO-GO 决策，**不自动部署、不替代运行时验证，也未在本轮 GitHub Actions 中执行**。

## 5. R1.2-F / 内核补丁准入条件

在确立下列条件前，**不提交“修复已完成”的 kext 补丁**：

- 查证与目标 macOS 15.5 **版本对应**的 IOGraphics/IOFramebuffer 和 IOTimerEventSource 执行语义。
