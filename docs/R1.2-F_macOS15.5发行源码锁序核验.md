## 2. 版本对应源码检查结果

在精确 IOGraphics `4d3fd008...` 与 XNU `a1e26a70...` 的源码上复核：

1. **`IOFramebuffer::stop` 先 SYS 后 FB**。构建 `SYSGATEGUARD(sysgated)` 后构建 `FBGATEGUARD(ctrlgated, this)`；随后可能在双 gate 内注销中断、移除事件源和回收对象。
2. **`IOFramebuffer::terminate` 同样先 SYS 后 FB**；其 `super::terminate(options)` 位于这两把 gate 获取之前。这并不改变函数后半段的锁顺序。
3. **两把门锁的身份**：`SYSGATEGUARD` 使用 `gIOFBSystemWorkLoop`；`FBWL(fb)` 指向 `fb->__private->controller->fWl`，即 framebuffer 控制器 workloop。
4. **getWorkLoop** 返回同一个控制器 workloop，与 R1.2-B 调用 `getWorkLoop()` 创建定时器一致。
5. **XNU 定时执行**：`IOTimerEventSource::timeoutAndRelease` 在 `wl->closeGate()` 与 `wl->openGate()` 之间调用 action；`IOWorkLoop::runAction` 也在该门锁内同步执行 action。
6. **事件源解绑与归还引用**：`IOWorkLoop::_maintRequest` 在 `mRemoveEvent` 分支调用 `setWorkLoop(NULL)` 和 `release()`；因此需要审查当前回调栈与引用销毁交错。
7. **Timer 模式**：无 options 的 `timerEventSource(owner,action)` 默认 priority kernel high，并采用 passive callback 路径，其 cancel 不能直接视为完整的所有外部 callback/owner 排空。
8. **Owner 所有权**：`IOEventSource::init` 保存了传入的 `owner` 指针，未对 owner 显式 retain；R1.2-C 的临时 owner/sender pin 正是为部分回调内部释放路径准备的，但不能解决反向获取 SYS 的问题。

精确源码中，`IOFramebuffer::stop`、`terminate`、`getWorkLoop` 与 SYS/FB 宏定义同公开默认分支**逐段字节一致**；虽然 IOGraphics 的整份源文件 Git SHA **不同**。对应 XNU 三份文件的 Git blob SHA 与本轮前所查询的默认分支文件相同。

这允许将 R1.2-D 的锁反转风险重新分类为：**在 Apple 官方 macOS 15.5 发布源码的锁获取顺序下存在条件性 ABBA 死锁时序**。但没有证据说明 HONOR 上实际已触发该交错、监听者一定调用 stop/terminate，或真实系统必然死锁。

## 3. 关键反例：引用计数足够≠锁顺序正确

```text
A = VBL timer dispatch on framebuffer-controller workloop
B = system termination thread

A: acquire FB
B: acquire SYS
B: request FB [waits for A]
A: external VBL proc -> synchronously stop/terminate -> request SYS [waits for B]

A waits for B; B waits for A. Retaining owner and timer does not break the cycle.
```

另有目标析构导致的隐式重入：`unregisterGate` 在 FB gate 内执行 `previous->release()`，当 refcount 归零时，`free()` 有可能触发未知的外部控制调用；此场景不是所有 listener 必然发生的行为，但目前也**没有上层契约能排除它**。
