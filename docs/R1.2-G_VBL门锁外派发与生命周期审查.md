## 1. 为什么需要这项研究

R1.2-F 已依据 Apple `distribution-macOS/macos-155` 发布清单锁定：
- `IOGraphics-599`：commit `4d3fd008c80d1414c9da8f02ea67d534b47158c2`；
- `xnu-11417.121.6`：commit `a1e26a70f38d1d7daa7b49b258e2f8538ad81650`。

R1.2-F [Actions #38209066259](https://github.com/Jakiewbe/honor-hackintosh-lab/actions/runs/38209066259) 成功核对精确源码，锁顺序为 `IOFramebuffer::stop/terminate: SYS → FB`。R1.2-C 的 VBL `IOTimerEventSource` action 则在控制器 FB gate 内调用外部 `snapshot.proc(...)`。**只有在外部 callback 或析构实际同步再入停止并且出现相应线程交错时**，才会构成先前模型中的 ABBA 循环；目前没有实机死锁报告。

本轮问题：是否能够把 VBL 监听者调用放在 **不持有 SYS/FB gate** 的上下文，同时保留注册、注销、使能和停止的线性化语义？

## 2. 公开 IOFramebuffer 监听者的实际代码

目标 macOS 15.5 IOGraphics 源码：
[Apple IOFramebuffer.cpp（固定 SHA）](https://github.com/apple-oss-distributions/IOGraphics/blob/4d3fd008c80d1414c9da8f02ea67d534b47158c2/IOGraphicsFamily/IOFramebuffer.cpp)，Git blob SHA `4763b2fc53cbcaeb2ad5c94531727975d6bc0ff8`。

`IOFramebuffer` 在显示设备初始化中通过 `registerForInterruptType(kIOFBVBLInterruptType,...)` 注册**自身的 `handleVBL`**，target 为 `this`，ref 为 `priv`（约第 9194–9202 行）。这不是抽象的无副作用回调。

`handleVBL` 的源代码约第 5265–5335 行：
- 读取 `GetShmem(inst)` 与 `inst->__private->actualVBLCount`；
- 更新 `shmem->vblTime`、`shmem->vblCount` 和 VBL 时间间隔；
- 调用 `semaphore_signal_all(inst->vblSemaphore)` 唤醒等待者；
- 根据启用的节流/通知状态，调用 `vblUpdateTimer->setTimeoutMS(...)` 或发起其他事件源通知。

而 `IOFramebuffer::stop`（约第 4402–4503 行）在持有 **SYS→FB** 两门锁时 `UNREGISTER_INTERRUPT(__private->vblInterrupt)`，移除 `vblUpdateTimer` 及其他事件源，并可能释放 `sharedCursor`。这说明 **out-of-gate 派发并不能仅靠 pin `target` 就证明对内部共享状态的访问安全**。即使目标对象引用还活着，关联的内部资源也可能已进入 stop/free 清理流程。

此外，官方 [IOFramebuffer.h](https://github.com/apple-oss-distributions/IOGraphics/blob/4d3fd008c80d1414c9da8f02ea67d534b47158c2/IOGraphicsFamily/IOKit/graphics/IOFramebuffer.h) 将 `unregisterInterrupt` 描述为移除已经注册的回调，**没有明确承诺可以容忍“注销返回后仍有未完成回调”**。因此不能擅自选择弱注销保证。

## 3. 三种方案的比较

| 架构 | SYS/FB 锁顺序 | 回调寿命与内部共享状态 | 研究判断 |
|---|---|---|---|
| **A：R1.2-C 当前 VBL action 内直接调用 `snapshot.proc`** | FB 内可能重新进入 SYS，存在条件性 ABBA 反例 | 引用保护减少 UAF，但无法消除锁顺序风险 | **不准加载** |
| **B：FB gate 内获取带引用票据，gate 外独立 worker 执行 `handleVBL`** | 若 worker 真的不持有 SYS/FB，则可避开上述直接 FB→SYS 路径 | 需要注销代际失效、进行中回调 drain、共享 VBL 状态同步、独立 worker 引用；worker 自身请求同步 stop 时有自等待风险 | **仅模型候选，不是驱动补丁** |
| **C：重新设计中断/通知边界，减少外部可重入调用** | 可能改善锁顺序，但必须确认 IOGraphics VBL 的真实行为要求 | 需要确认屏幕更新、VBL 计数与通知时序；不允许静默删除或伪造 VBL | **研究保留，暂无实现证据** |

最关键的新风险：**自等待（self-join）**。假设架构 B 的 worker 正在执行 `handleVBL`；若它同步调用 `IOService::stop`，而 stop 为保护共享状态必须等待所有进行中的 worker 结束，则可能出现：

```text
VBL worker:  handleVBL(...) -> synchronous stop(...) -> wait active VBL count == 0
stop:        cannot return until active worker count == 0
VBL worker:  cannot decrement count until synchronous stop(...) returns
```

即便此时没有 SYS/FB ABBA，两者也可能因为**等待自身完成**而形成循环；不能把 `stop` 改为只排队然后返回“已完成”。

## 4. 非内核参考模型：callback ticket + epoch

[tests/test_r12g_vbl_ticket_model.py](../tests/test_r12g_vbl_ticket_model.py) 是本地执行过的纯 Python 状态机，不链接任何 Apple/NVIDIA 源码。它**假定**存在独立 worker 和适当的同步，模拟如下协议：

1. **Capture（FB gate 内）**：只复制当前 callback 槽，固定 `target`、`owner` 寿命，保存 registration `epoch`，并限制同一时刻至多一个待派发票据；本阶段不执行监听者。
2. **Release gate → Dispatch（FB gate 外）**：worker 在正式调用之前重新核对当前 `phase/epoch/enabled/slot`；如果注销/停用/停止发生在队列等待期间，必须丢弃过期票据、平衡引用，不调用过期监听者。
3. **Unregister/Stop**：注册槽的所有权转移和失效操作要有同步线性化点；持锁状态下不触发可能再入驱动的外部 target 最终析构。
4. **Drain → Finalize**：已经开始的回调仍持有 target/owner 引用；停止不能在仍有回调或队列票据时释放其所依赖的内核资源。
5. **同步停止的拒绝条件**：`callback_requests_synchronous_stop()` 显式返回 `BLOCKED_SELF_JOIN_AND_SHARED_STATE_UNPROVEN`，这只是研究阻塞标记，**不是提交给 IOKit 的可用返回值或 driver 行为**。

本地实际执行：**16/16 个 `unittest` 成功，深度 8 遍历 363 个状态**。覆盖 queued ticket 被注销/禁用/重新启用失效、active 回调下注销和停止、禁止提前 finalize、引用平衡、重复请求等。模型没有真实线程调度、条件变量、真实内核锁、对象析构副作用、跨 CPU 内存顺序、VBL 时序或 IOFramebuffer 内部对象，因此**不能据此证明方案 B 安全**。

## 6. 决策、阻塞与下一阶段

**已经明确：** 门锁内同步外部回调不是安全默认方案；简单 out-of-gate 转发同样不是安全默认方案。两种设计分别有 ABBA 和自等待/共享状态并发风险，不能用模型通过代替 IOKit 运行时验证。

**P0 未解决：**
- `IOService::stop` 的同步完成语义，以及从 worker 当前 callback 中触发 stop 的合法退出机制；
- `IOFramebuffer::handleVBL` 对 `__private`、`StdFBShmem_t`、`vblUpdateTimer` 等资源的并发读写与 stop-time drain；
- `unregisterInterrupt` 返回时对已开始回调的可观察完成保证，以及回调触发目标析构时的重入；
- 实际注册/注销、refcount、worker 队列、控制器/系统 gate 的锁顺序与 timeout/cancellation 最终完成证明。

**P1 未解决：** 独立派发引入延迟与 VBL 抖动，影响 WindowServer、VBL 计数和 GPU/显示器同步行为的可能性，尚无可量化数据。

**R1.2-H 建议**：优先核对 `IOFramebuffer` 对 VBL callback 的实际时序与锁要求，并研究是否存在不需要新异步 worker 的严格安全路径；若没有可靠方式满足共享状态与 stop 语义，明确放弃该内屏模拟驱动路线，转向只读硬件 GPU 走线及 NVIDIA 原生驱动可行性证据，不投入高风险补丁。

**正式结论：`R1.2-G MODEL-ONLY / RUNTIME_NO_GO`。**
