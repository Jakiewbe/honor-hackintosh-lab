### 本次要审查的设计命题

## 1. L1 的真实最小成功条件不等于“提供一个 IOFramebuffer 类”

必须分开验证三个客观事实：

- **硬件事实**：eDP 输出持续开启，管线/PLL/Power Well、Plane、Scanout Surface、Pitch、Pixel Format、Tiling 与 CPU 写入或复制路径全部有效；不能只从 PCI ID 或 VRAM 信息猜测。
- **macOS 内核事实**：同版本 `IOFramebuffer` 的 `enableController`、`getApertureRange` / `getVRAMRange`、`getDisplayModes` / `getInformationForDisplayMode`、`getPixelInformation`、`getCurrentDisplayMode`、`setDisplayMode`、连接、通知与停止行为符合真实客户端；callback 注册/注销必须确实同步清理。
- **用户可观察事实**：实际的 macOS 15.x WindowServer 将该接口作为在线显示设备，界面持续更新且能输入，停止/重启无损坏。现代 macOS 对无加速驱动是否提供足够的软件渲染回退，目前**未经本项目真实硬件验证**，不能凭 `IOFramebuffer` 类存在断言必然显示桌面。

Apple **macOS 15.5 pinned IOGraphics-599** [`IOFramebuffer.h`](https://github.com/apple-oss-distributions/IOGraphics/blob/4d3fd008c80d1414c9da8f02ea67d534b47158c2/IOGraphicsFamily/IOKit/graphics/IOFramebuffer.h) Git blob `8bf176f408ccaf902f0c07689a3785c8efabb5a4`，及 [`IOFramebuffer.cpp`](https://github.com/apple-oss-distributions/IOGraphics/blob/4d3fd008c80d1414c9da8f02ea67d534b47158c2/IOGraphicsFamily/IOFramebuffer.cpp) 已复核。此版本源码中未找到 `IOFramebuffer::setConfiguration` 或 `IOFramebuffer::validateMode` 这两个具体方法定义；**不能声称 WindowServer 一定调用它们**。正确研究对象是已有的 display mode、pixel information、aperture、power/event APIs。尤其 **`getInformationForDisplayMode` 返回模式元数据，不是将物理扫描基址交给 WindowServer 的接口**；物理 framebuffer 相关契约涉及 `getApertureRange` 与内存描述符。

## 2. GOP、VBT、Stolen Memory、GGTT 是四件不同的事

- UEFI **GOP**：固件提供图形输出及 framebuffer 启动状态；启动阶段是否由固件保持 Intel eDP pipe/plane/clock，需硬件和后续 OS takeover 的证据。
- **VBT**：Intel 显示板级配置（eDP/port/panel/backlight）的一类固件数据，不是 GOP 本身；正确使用要核对 ACPI OpRegion 等来源，不能把两者当成同一交接协议。
- **Stolen Memory**：被固件保留、不能由普通 OS allocator 占用的一段物理内存，未必全部可用，未必全都作为显示 plane 存储。Intel 官方 [12th Gen BDSM register](https://edc.intel.com/content/www/us/en/design/publications/12th-generation-core-processor-datasheet-volume-2-of-2/base-data-of-stolen-memory-bdsm-0-0-0-pci-offset-b0/) 把 `0xB0` 归属 Host Bridge PCI **00:00.0**，记录一段 stolen DRAM **基址**，并不等于 Intel graphics PCI 00:02.0 的 `0xB0`，也不提供活动 scanout 对象偏移、stolen size、tiling、reserved/usable region。
- **GGTT**：GPU 图形地址转换；某个 GGTT 偏移可能映射多种 backing，也可能被重映射；`GGTT 0x0` **不等于** `BDSM physical base` 或当前扫描 plane 的起点，且未验证这个 BIOS 是否把保留区域从 0 映射。

精确上游反证：[Linux v6.1 的 `i915_gem_stolen.c`](https://github.com/torvalds/linux/blob/830b3c68c1fb1e9176028d02ef86f3cf76aa2476/drivers/gpu/drm/i915/gem/i915_gem_stolen.c) 第 49–51 行对新版 iGPU 跳过 stolen 的第一页；第 421–503 行扣除 reserved 区，按可用大小再初始化 `drm_mm`。 [`intel_ggtt.c`](https://github.com/torvalds/linux/blob/830b3c68c1fb1e9176028d02ef86f3cf76aa2476/drivers/gpu/drm/i915/gt/intel_ggtt.c) 包含 PTE、映射以及某些状态切换时的清除操作；不能将 BIOS 初始化的 GGTT 形态视为 OS 启动后的不变契约。

**禁止实施**：直接以 `BDSM + 0` 或假定 `GGTT + 0` 写测试像素、把整段 stolen memory 包装为可让 macOS 任意写入的 `IODeviceMemory`、跳过地址所有权检查、跳过 `drm_client_buffer_vmap` 物理页检查而直接声明 `contiguous`。该思路只能作为需要先证明的内存来源候选，不能作为已验证“突破口”。

## 3. 固件接管 vs 最小 i915 KMS：两条路径不应在一个第一阶段强行合并

| 线路 | 需实现的内容 | 最容易误判的前提 | 研发决策 |
|---|---|---|---|
| **A 固件保持模式** | 只在**已验证**现有 plane、pixel layout 和映射所有权时，提供安全的只读观测和必要的 IOFramebuffer 接口 | UEFI GOP 画面≠macOS 接管时仍有有效 pipe/plane；不能默认线性 XRGB8888 | 保留作为**早期条件性路线**，不能预判一定只能临时；不证明就停 |
| **B Intel-only i915 KMS** | 固定 Alder Lake-P 设备、VBT/OpRegion、显示 Power Well / CDCLK / PLL、eDP AUX/link training、GEM/GGTT backing、DRM→XNU 映射、IOFramebuffer 生命周期 | “没有渲染”≠“显示不用 GEM/同步/电源” | 保留为可逐段自主移植的主研发路线，先做依赖图再裁剪 |

**CPU 软件渲染和 GPU KMS 必须分开**。macOS 是否允许一个第三方无加速 `IOFramebuffer` 在 macOS 15.x 构成在线桌面是独立 runtime gate，不可当作已知真命题。

## 4. 反对几类危险的“便捷裁剪”

1. **GuC/HuC/DMC：不可一刀切。** GuC/HuC 常涉及 GT 调度/媒体功能，L1 可以在查实不需要的情况下暂缓；**DMC 是 Display Microcontroller，与 display power state 相关**。Linux 6.1 [`intel_dmc.c`](https://github.com/torvalds/linux/blob/830b3c68c1fb1e9176028d02ef86f3cf76aa2476/drivers/gpu/drm/i915/display/intel_dmc.c) 明确包含 `ADLP_DMC_PATH`、目标版本；[`intel_display_power.c`](https://github.com/torvalds/linux/blob/830b3c68c1fb1e9176028d02ef86f3cf76aa2476/drivers/gpu/drm/i915/display/intel_display_power.c) 管理 `POWER_DOMAIN_DC_OFF` / power wells。只有在证明特定最小显示状态不需某 firmware、且其受影响的电源状态被真正禁止后，才能停用部分功能。不能假装 firmware load 已成功。
2. **PM/runtime 功能不可一律 `return 0`。** `0` 是 Linux 内核通常的成功值；如果没有实际保持 Power Well、锁住 DMA/GEM 对象、完成 MMIO/PLL/PHY 操作，调用方会错误地继续下一个硬件步骤。未支持时明确返回 `-ENODEV`、`-EOPNOTSUPP` 或 fail-closed；并在调用方证明该功能是**可选**时才跳过。必需功能缺失→整个初始化 BLOCKED。
3. **锁/等待/工作队列不能机械替换。** `msleep→IOSleep` 仅在可睡眠线程语境可能成立；`usleep_range` 不总能等价 `IODelay`（忙等 vs 让出 CPU）。Linux spinlock 的 IRQ、禁抢占及内存顺序语义不能仅凭 `IOSimpleLock` 复刻；`workqueue` 也不等于 `IOTimerEventSource` 或同步 `IOCommandGate`。先按 context（IRQ/softirq/workloop/thread）分类，再定义 XNU 上的原子、锁序、等待和对象 lifetime。
4. **不要从文件名直接定义最小 i915 集。** Linux v6.1 的 `drivers/gpu/drm/i915/display/` 存在 `intel_dp.c`、`intel_dp_aux.c`、`intel_bios.c`、`intel_panel.c`、`intel_combo_phy.c`，但**没有单独的 `intel_edp.c`**；eDP 逻辑位于 DP/panel 等文件中。v6.1 GGTT 主实现是 `gt/intel_ggtt.c`，不是可直接拿来单独编译的 `i915_gem_gtt.c`。裁剪必须来自**目标版本真实源码和调用图**，不能照搬某个网上的固定文件矩阵。
5. **C/C++ 隔离原则正确，但 `.a` 中“零未定义符号”不是合理的通用验收条件。** 普通静态归档可保留在最终链接时解决的外部符号；应跟踪**每个对象所需符号→真实定义/受许可 kext 导出**，最终对 macOS kext ABI 检查未解决强符号，不以禁用全部外部引用或假实现换取表面通过。
6. **现代 macOS 内核扩展验收**：`kext` 可静态链接不等于可加载、可正确匹配设备或通过安全策略；我们不绕过系统安全机制，不签名/安装/加载未审查驱动。可编译对象或完整静态链接只许记为 `BUILD_ONLY`。

## 6. 修正后的 R1.4-B 动手顺序（有信息增量的工作）

**B0：源码和用途定界**：选择并固定上述同版本**候选** FreeBSD DRM 6.1 / Linux 6.1，同时确认 FreeBSD base 的具体可兼容版本及 Git commit；如版本差异破坏 API/ABI，一律先记录，不通过危险 Stub 绕过。

**B1：目标调用图**：从 `INTEL_ADLP_IDS → i915_pci_probe → display init → VBT/OpRegion → power/CDCLK/PLL → eDP/AUX/link training → plane/scanout → IOFramebuffer` 逐段标明 source file / defined symbols / required services。按调用路径识别真正需要的 DRM core、LinuxKPI、内存和调度实现，绝不以文件名做盲删。

**B2：兼容性契约**：对每个 LinuxKPI 函数分类为 `implemented-with-equivalent-semantics` / `optional-explicitly-unsupported` / `required-blocked`。**禁止对未初始化的 MMIO、内存、固件和锁返回成功。** 实现必须具备单元测试的锁序/对象 lifetime 与错误传递，编译警告不得大面积屏蔽。

**B3：独立的版本锁定编译**：macOS Intel SDK 上针对实际选定文件编译，构建时从清洁对象目录开始；`missing sources=0`、每文件源/对象 hash、编译失败=0、最终链接的未解决强符号有明确归因、license inventory 已审查。出错 FAIL-CLOSED，不用旧对象凑链接；输出纯文本证明，不发布可安装 kext。

**B4：内存及 GPU 输出接口核查**：分别证明 stolen RAM 的 reserved/usable boundaries、GGTT mapping / aperture 地址、active plane surface + pitch/format 与 XNU 内存描述符之间的合法映射。若不能证明，**只读结束，不通过写入未知物理地址探索**。

**B5：仅后续隔离硬件运行**：当源码闭包、并发/stop、失败回滚经审核，并且有非主力 Intel Xe 相容机器与独立恢复手段时，才能进入首次真实 IOFramebuffer/WindowServer 验证。任何虚拟机/host CI 成绩均不得冒充真实内屏。

> **L1 真实成功标准**：不是“`AlderFB.kext` 编译链接完成”，而是“真实目标显示器收到并持续刷新 macOS 画面，WindowServer 可操作，资源清理与重启可证明安全”。

当前 **R1.4-B 仅完成 critical design review 和独立候选源码定位**；没有创建项目驱动构建或声称链接成功，也没有触及用户主力 Windows、BIOS、EFI、内核扩展安全策略。
