## Context

I'm researching the reproducibility of `NMXGPU.kext` from the **v1.14.2 release** (source commit `1083a98db33a0bb824290556de255f9a95ca5403`), specifically the Intel i915 path for Alder Lake-P `8086:46A6`. This is a **source-only investigation**; no driver has been loaded on the target computer.

I appreciate that `gpu-port/README.md` already says the AMD/Intel GPU port has not been loaded on physical GPU hardware. I'm not asking for a compatibility or functionality guarantee.

## Precise reproducibility questions

The published `gpu-port/xkpi/all-i915.sh`, `cc-i915.sh`, `rt.sh`, and `kext/build.sh` refer to external build trees under `/Volumes/MiniData/build/gpu-src/`. Could you please point me to an existing artifact, documentation or text manifest that identifies the **actual input used to build the released NMXGPU binary**?

1. The precise repository URL / Git commit (and any local modifications) for the `kpi/drm-kmod`, `kpi/freebsd-src` and `linux-6.14` trees. SHA-256 file manifests would also work if those trees were not clean Git checkouts.
2. The generated `amd.flags`, `srcs-i915.all`, `srcs-i915.txt` or their exact checksums, plus any unresolved source-list diagnostics (`#MISSING`).
3. Whether the release build had **zero failed i915 compilations**, and whether its `obj-i915` directory was clean. A source-to-object inventory and object count is sufficient; binary objects are **not** requested.
4. A final `NMXGPU.kext` build/link manifest or map that ties the compiled `i915_pci.c`, `intel_display_device.c`, eDP/AUX, GGTT and DRM framebuffer bridge objects to the published binary.
5. The published `nullmoth-nvidia-1.14.2.tar.gz` has now been SHA-256 verified and its **172 archive paths** inspected in an [independent read-only inventory](https://github.com/Jakiewbe/honor-hackintosh-lab/actions/runs/38217837373). The package contains the `NMXGPU.kext` binary, but **none of the expected filenames** (`amd.flags`, `srcs-i915.txt`, `obj-i915/`, drm-kmod/FreeBSD/Linux source trees or build/link manifests). If the build records exist under other names or in a **separate public asset**, a path/link reference would be very helpful.

Why this matters: `srclist.py` prints missing source entries to stderr, but `all-i915.sh` redirects that stderr to `/dev/null`; it reports compiler failures but doesn't unconditionally reject a nonzero failure count, and `kext/build.sh` links `obj-i915/*.o` without a source/object manifest check. These are potential **build-evidence gaps**, **not an assertion** that your released binary was built incorrectly.

For reference, your `kext-npu/mksource.sh` and the `nmxnpu-source-1.14.2.tar.gz` release asset already demonstrate a compiler-dependency manifest approach for NMXNPU; I'm looking for analogous reproducibility evidence for the **NMXGPU i915** stack.

For that inventory, the upstream-published SHA-256 and actual downloaded SHA-256 both were `7c7f7ac97dbcdd48786d4384ffcb2d19199b6d3bc0fb013c71f63b766dea6be5`. The result is **not** a claim that the shipped binary is incomplete; only the specific public archive paths were inspected.

Thanks for any pointers. A short text response with the commits and paths is enough; there is no need to share machine-identifying logs, private files, binaries or proprietary material.
