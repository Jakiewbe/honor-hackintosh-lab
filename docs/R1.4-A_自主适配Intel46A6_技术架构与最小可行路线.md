# R1.4-A｜HONOR GLO-FX6P 自主 Intel 46A6 图形适配：架构、瓶颈与最小可行路线

**研究基线：2026-10-12；状态：OWN-PORT-DESIGN / NO_NATIVE_BUILD_YET / NO_RUNTIME_HARDWARE / RUNTIME_NO_GO。**

**审查修订提示**：后续 [R1.4-B 第一性原理/源码审查](R1.4-B_方案批判性审查与独立源码基准.md) 已明确：
- 先做 L1 基础内屏是研究目标而非保证 WindowServer 必然支持无加速桌面；
- BDSM host bridge 基址、BIOS stolen memory、GGTT 偏移、实际 plane scanout 地址**不可混同**，禁止假定 GGTT 0 就对应可覆写的 stolen 起始物理地址；
- LinuxKPI 不能机械转换同步/锁/工作队列，关键硬件初始化/固件/PM 绝不使用 `return 0` 的假成功 Stub；
- 优先复核 FreeBSD drm-kmod **6.1-lts** 与 Linux **v6.1** 同系列独立候选，兼容性和 FreeBSD base 源码尚未闭合；
- 自主 native kext BUILD-PASS 不等于“可加载”或真实 macOS 内屏点亮。

本页 R1.4-A 为总体研究方向，R1.4-B 对容易引发内核风险的具体实施建议拥有更高技术优先级。

## 1. 最终目标与三层独立的成功定义

| 层级 | 目标 | 客观验收 | 当前状态 |
|---|---|---|---|
| L1 基础图形 | HONOR Intel 内屏持续显示 macOS 桌面，即使无 3D 加速 | 非主力 Alder Lake-P / 同 PCI 硬件：完整从 macOS boot handoff → IOFramebuffer published → WindowServer online display → 连续更新像素并允许输入、重启/停止不死机的独立记录 | **未验证** |
| L2 Intel 图形加速 | Intel i915 的命令提交、内存管理与 macOS 用户空间图形设备 | 真实 GPU 负载、可重现的 Metal/IOAccel 查询及渲染/同步数据，非 mock，持续运行与故障恢复 | **远未验证** |
| L3 NVIDIA 混合显示 | RTX 2050 真正渲染并交付 Intel 内屏 | 两块 GPU 的具体驱动/PCI ID、完整渲染→复制/同步→Intel scanout、性能及资源回收日志 | **远未验证** |

**目前开发只瞄准 L1**，并设置两个可选工程路径：

- **A：Firmware framebuffer handoff（短程低侵入候选）**。尽量让 UEFI/GOP/固件已点亮的 Intel scanout 继续工作，再通过经审核的 Intel framebuffer 映射发布 IOFramebuffer；与旧 `NMIntelFB::adoptFirmwareMode` 思想相近。前提是固件留下活动 pipe 且它的像素格式、tiling、buffer 映射与同步行为可由 macOS 正确接管。该前提**对 GLO-FX6P 尚未验证**；若失效，**停止追补，不猜测 MMIO 地址**。这只能尝试无加速桌面，不能宣称完成 Intel KMS 或 Metal。
- **B：Independent Intel i915 KMS port（主研发候选）**。将可固定版本的 FreeBSD/Linux i915 + 必需 DRM core/LinuxKPI/XNU IOKit shim 组成**最小 Intel-only 驱动**；先只做 Alder Lake-P 46A6、内屏单输出、XRGB8888、固定模式的 DRM framebuffer→IOFramebuffer 路径，不同时构建 AMD/xe/NVIDIA 或虚构 Metal 加速。由于现有 NMXGPU 的共享 DRM core 可能依赖 AMD 对象初始化，**最小依赖边界需先以 undefined symbol /链接对象 manifest 核实**，不能直接删除对象后假设可用。

**先在静态层并行核查 A/B，运行时只在隔离设备拥有恢复渠道后选一条进行真实测试。** L1 跑通后才讨论 L2；不要让 RTX 2050 阻塞 Intel 内屏问题。

## 2. 自研真正困难的 7 个层次（不是加 PCI ID）

1. **基础 XNU/FreeBSD/Linux ABI**：LinuxKPI/DRM `struct device`、PCI resource/interrupt、mutex/workqueue、GEM、DMA-fence、clock/timer、`kmalloc`、PCI config space、IOMMU，以及 XNU 的任务地址空间和 `IOService` 生命周期语义不同。**对象编译和链接不是内核运行正确性证明**。
2. **硬件 bring-up / GT 与 display**：Intel `8086:46A6` ADL-P i915 PCI probe 后需要确认 MMIO BAR/GGTT/stolen memory、VBT/ACPI OpRegion、电源井、DMC/GuC/HuC 相关固件和失败回退；不能假设 Linux 驱动在 XNU 上运行就具有同样的固件与电源状态。
3. **eDP KMS**：AUX、DPCD、面板电源时序、link training、transcoder/pipe/plane、分辨率/时序和背光。eDP 线缆归属 Intel 已知，但**成功 PCI probe 不等于显示通道成功**。Linux DRM [KMS 官方文档](https://docs.kernel.org/6.15/gpu/drm-kms.html) 将 connector/CRTC/plane 独立建模。
4. **GGTT/GEM 与 macOS framebuffer 的物理背书**：现有 `nmx_fb_bridge.c` 用 `drm_client_framebuffer_create` + `vmap`，要求所有页面经 XNU `pmap_find_phys` 对应 CPU 物理连续的 `IODeviceMemory::withRange`。**GPU GGTT 虚拟连续与 CPU 物理连续不同**；能否满足取决于实际 backing（可映射的 BAR aperture / 连续 RAM / 普通 scatter-gather）及缓存同步。绝对禁止为求通过而伪造物理连续或把 RAM scatter 映射成单一物理范围。若当前方式不成立，应设计有合法描述符/稳定连续 staging buffer 的复制链，并逐一证明所有权、锁定、同步与刷新，而不是直接 patch if。
5. **WindowServer / IOGraphics 接口**：正确 IOFramebuffer 发布、VRAM/aperture ownership、模式/像素布局、online display 与 cursor/VBL/event 交互。Apple 官方明确把 `IOFramebuffer` 标为 **Deprecated**，说明其只有基础 framebuffer 能力且不建议第三方使用：[Apple IOFramebuffer](https://developer.apple.com/documentation/kernel/ioframebuffer)。应用级 Metal 是更高的一层。
6. **内核并发安全与恢复**：`NMXGPUFB::unregisterInterrupt`、`setInterruptState` 当前空实现；原始 timer 直接调用注册回调；`stop` 同步等待 timer、`nmx_fb_unpublish` 同步 `terminate`，可能形成并发生命周期安全漏洞。 R1.2-D/E/G 已提供适用于**抽象风险意识**的模型，但不能直接移植到新代码。修复应等资源链可追溯后以 release/acquire、epoch/ticket、stop completion 和 FB Gate 锁序证明。
7. **Intel Metal 与 NVIDIA+Intel 的完整图形层**：Metal 的用户态设备、shader 编译、命令缓冲、IOAccelerator/WindowServer 协议**不是** Linux `i915.ko` 本身自带的功能；从 Linux ANV/Vulkan 翻译到 Metal 非简单调用已有 MoltenVK（该项目通常做 Vulkan→Metal 的反方向封装）。NVIDIA 必须再完成 GSP、RM、NVAccel 与 cross-GPU copy/同步，开销和黑屏风险显著提高。**L2/L3 严格后置。**

另外设置独立 **P0-PLATFORM**：i5-12500H P/E 混合核心、macOS CPUID/kernel、ACPI、EC、NVMe 等平台启动支持没有作为完整实机条件验证。 即使 display driver 完成，也不能自动宣称整机可启动。

## 3. 独立开发的版本/许可策略

建立自有 `HONOR-i915` 代码/构建分支时：
- **明确区分研究档案与产品代码**，保留现有已归档实验，不在 `main` 覆盖 NullMoth 上游文件或历史补丁；有代码实现时建议独立 Git 分支和分级 PR。
- 固定**本项目可复现的输入**：候选参考 FreeBSD [drm-kmod `c16de0f9fa84f70b9551f69fde837a7f3a73c0e9`](https://github.com/freebsd/drm-kmod/tree/c16de0f9fa84f70b9551f69fde837a7f3a73c0e9)（*候选；仅用于自研，**不称为 NullMoth 真正编译源***）、FreeBSD src 的**待选独立 Git SHA**、Apple 15.5 IOGraphics/XNU 的 **R1.2-F 已固定 commit/blob**、对应官方 SDK/Xcode 环境。
- 基于 ADL-P 使用 i915，暂不引入 xe/AMD，**先核对 DRM core 与 LinuxKPI 真实依赖**；所有抽取的源码路径、许可证、补丁、宏/编译参数、生成文件、对象 SHA-256、未解决符号均完整归档，若失败则 FAIL-CLOSED；不存在的源码和固件不能凭名字补出来。
- Linux i915/DRM 含 GPL 与多种 dual-license 文件；**逐文件许可审计**并确认移植、分发的权利与义务；不同许可证的二进制混合/分发问题不得未经审查直接发布。GPU firmware 单独核对许可和版本。
- 构建工作流只允许 `workflow_dispatch` 手动触发，`macos-15-intel` 等托管 Runner 仅编译/做负向静态检查，**不能加载 kext、改 SIP、签名、重启、触碰实机**，默认仅上传纯文本 build manifest；不得把绿色编译当 GPU 成功。

## 4. 自主研发分阶段工作计划与 FAIL-CLOSED 门槛

| 阶段 | 最小成果 | 验收 / 停止条件 | 是否需要硬件 |
|---|---|---|---|
| **R1.4-B｜依赖闭包** | 自主锁定 i915 + DRM core + BSD/XNU glue 源码；生成稳定 `source→object` 清单、逐文件 license/hash、`#MISSING=0` | 找不到正确许可证/头文件或未解决符号无法定位即 **BLOCKED**；不得用旧缓存对象 | 否 |
| **R1.4-C｜Intel-only native objects** | 真实 `8086:46A6` 匹配 + i915 KMS + DRM + shim 独立编译和链接在 macOS 15.5 SDK | 所有期望对象 SHA 可核对，`compiler-fail=0`，`undefined` 归因明确；**仍标 SOURCE/BUILD-ONLY** | 否 |
| **R1.4-D｜scanout 语义审计** | 证明 dumb/GEM 对象、`vmap`、XNU 描述符与 eDP scanout 的合法 backing；必要时先设计经过固定 buffer copy 的最小桥接 | 任意 CPU/GPU 地址类型被混用或无法证明内存生命期→停止开发，不做“绕过连续性检查”补丁 | 否 |
| **R1.4-E｜生命周期安全** | Apple 15.5 IOGraphics 的 stop、VBL、注销/清理契约与新 Intel FB 实现匹配 | 负向并发模型与代码审查无已知 self-join/ABBA/UAF；**抽象模型不代替实机** | 否 |
| **R1.4-F｜隔离硬件原型** | 仅在**非主力、具备恢复通道**的 Alder Lake-P / 46A6 实物中观察 probe、VBT、eDP、framebuffer + WindowServer | 黑屏、CPU/GPU hang、firmware power reset、内存映射异常均立即停止；无独立设备就保留 PENDING | **必须** |
| **R1.4-G｜硬件加速可行性** | 若 L1 成立，再调查 Intel ANV/IOAccel/Metal；NVIDIA RTX2050 另开独立证明 | 无真实渲染就不能升级到图形加速已用 | **必须** |

**重要取舍**：
- 能马上开始的是 **R1.4-B 独立源码闭包**，不是在主力荣耀安装驱动；
- Firmware framebuffer handoff 应保留为 **较窄的 L1 快速假设**，以只读证据判断是否值得进一步投入；
- 当前没有真实 macOS Intel Xe 的物理测试环境；因此最多完成源码、编译、并发与缓冲区设计审查，**不能宣布 Intel 内屏已适配**；
- 不重复已完成 R1.2/F/G、R1.3-D 资产目录审查，不等待 Issue #146 才能启动本项目自己的可复现源码构建。
