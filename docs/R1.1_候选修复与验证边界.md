## 1. 实际修复范围

| 问题 | 原版状态 | R1.1 候选修改 | 仍缺的证据 |
|---|---|---|---|
| Intel BAR0 MMIO 边界 | 直接使用 `fMMIO->getVirtualAddress()` 对寄存器偏移做解引用 | 在第一次 `rd()` 前校验虚拟映射地址及 `getLength() >= 0x731A0`，失败直接停止接管 | 原生编译、实际 BAR0 长度和寄存器安全性 |
| Intel `nvScanoutInfo` 容量 | 扫描面 `actualSize=0`，但返回非空 `kva` | 返回 `fSurfMap->getLength()`，同时校验有效映射、非零几何、对齐、最后一行有效像素范围 | 当前结构体只能提供容量，尚未在驱动生命周期上建立强引用/同步 |
| NVIDIA→Intel 复制 | `performTransaction` 仅比较宽高并拷贝最小 pitch，未核验目标容量 | 使用 `q.actualSize` 校验最后一行目标像素范围；已有 NVResource 映射来源核验进一步收紧；只复制 `width*4` 活动像素，而不是 padding | NVAccel 仍缺 Darwin r610 构建参数，**不能原生编译验证** |
| 异步 flip | 未审计的 `thread_call` 延迟翻转入口仍可进入 | **切断现有入口的异步入队调用**，保留已有同步翻转路径 | 仍保留历史异步实现；完全移除/重构以及关闭时的所有权语义需另行处理 |

两条容易混淆的边界：

1. **R1.1 没有更改 `NVRMVramRequest` ABI 布局**。而且已确认上游 `NVRMFB` 使用同一 `actualSize` 字段，本补丁是修正 Intel 生产者和 NVAccel 消费者契约。
2. **复制目的地容量校验不是内核显存安全的完整证明**。映射释放/重配仍可能与持有 `kva` 的调用并发；VBL、通知回调、会话 teardown 仍须独立审计。

## 2. 测试与证据登记

- 在本地 Linux 的纯 Python 环境中，`tests/test_r10_bounds_model.py` 的 **13/13 项数学边界参考测试通过**。覆盖零容量、尺寸无效、截短源与目的地、行跨度、不对齐、64 位溢出和 BAR0 下界。
- 模型测试**只验证建议采用的数值安全合同**，不编译原版或修改后的内核驱动，更没有执行 `NVAccel`。
- R1.1 工作流会在 `macos-15-intel` 执行：固定 Commit 完整性 → `git apply --check` → 应用补丁 → `git diff --check` → 逆向校验 → 源码检查 → 13 项模型 → **仅编译、链接 NMIntelFB** → 保留纯文本日志。
- `NVAccel` 因 NVIDIA 官方 `610.57.04` 缺少 `Darwin_x86_64/compile_cmds.sh`，本轮**没有完整原生编译**，不得写为“补丁编译通过”。
- GitHub Actions 工作流需要手动触发，不设置 push/schedule 触发器，不上传 `.kext` / `.o` / 可执行文件，不加载、不安装、不代码签名。

## 4. 运行/回退方式
