## 关键 XNU 事实：为什么 B 版编译通过仍不安全

1. XNU `IOEventSource::init(OSObject *inOwner,...)` 将 `owner = inOwner`，并**没有对 owner 做 retain**。见 [IOEventSource.cpp](https://github.com/apple-oss-distributions/xnu/blob/main/iokit/Kernel/IOEventSource.cpp)。
2. `IOTimerEventSource::timeoutAndRelease()` 为排队任务提供 event source/workloop 的引用保护，但不能据此推断它拥有外部驱动 `NMIntelFB` 的生命周期。见 [IOTimerEventSource.cpp](https://github.com/apple-oss-distributions/xnu/blob/main/iokit/Kernel/IOTimerEventSource.cpp)。
3. `IOWorkLoop::runAction` 在**可重入 gate** 下执行；来自 VBL action 的外部监听者可能同步调用 `unregisterInterrupt`、`stop` 或触发析构。见 [IOWorkLoop.cpp](https://github.com/apple-oss-distributions/xnu/blob/main/iokit/Kernel/IOWorkLoop.cpp)。
4. R1.2-B 的 `vblFire` 在 `snapshot.proc(...)` 返回后仍访问 `me->fVblCalls`、`me->fVblPhase`、`me->fVblTimer`，此前没有显式固定 `me` 的引用。因此**条件性 UAF 风险真实存在于代码结构中**；没有发生过实机崩溃的证据。

## 本轮修复的精确范围

R1.2-C 在 VBL 回调检查已处于 `ARMED`、timer identity 匹配后，增加对 `me` 和 `timer` 的 **retain**，并维持这些引用直到：

- 外部 `snapshot.proc(snapshot.target, snapshot.ref)` 返回；
- 当前监听者的快照对象引用已释放；
- 已再次检查驱动仍是 `ARMED` 且 timer 未被替换；
- 仅符合上述条件时才计算刷新周期并尝试重排队；
- 最后按顺序 `timer->release()`、`me->release()`，**最后一行之后不再解引用 me 或 timer**。

这次修复针对**回调栈在同步卸载或注销后继续访问对象**的特定悬空引用窗口；不改变 ABI 布局，不恢复 R1.1 禁用的 NVAccel 异步 flip 入队，不修改物理 GPU 代码或上游仓库。

### 源码交叉检查与下一阶段优先级

Apple XNU [IOTimerEventSource.cpp](https://github.com/apple-oss-distributions/xnu/blob/main/iokit/Kernel/IOTimerEventSource.cpp) 中，无 options 的 `timerEventSource(owner, action)` 默认使用 `kIOTimerEventSourceOptionsPriorityKernelHigh`，采用 `timeoutAndRelease` 的 **passive timer** 路径；其 `cancelTimeout` 在该路径调用 `thread_call_cancel`，不是无条件的 `thread_call_cancel_wait`。因此不能错误地声称**当前** timer 默认会在 `stop()` 自身回调中必然发生 `cancel_wait` 自等待死锁。

但还有运行时无法凭 CI 证明的风险：`stopGate`、`disarmVbl`、`removeEventSource` 与外部 VBL 目标析构之间存在可重入控制流；R1.2-C 的 owner/sender retain 降低了一个悬空引用窗口，却没有证明所有 stop/free 阶段合法，也没有验证实际 WindowServer 与 kernel collection 的配合。

**R1.2-D（提议）** 应先审查 `IOWorkLoop::removeEventSource`、`IOTimerEventSource::timeoutAndRelease`、`IOFramebuffer::stop` 的同步再入次序，建立包含外部目标析构回调的最小依赖图和负向模型，再决定是否改动生产补丁。重复原生构建不会提供新的运行时证据。

**阶段门禁：REAL BUILD-PASS / VIRTUAL BUILD-PASS / RUNTIME-BLOCKED。** 主力 HONOR GLO-FX6P 的 Windows、EFI、BIOS、磁盘不修改，不进行未经证明的驱动安装、签名、加载与实机试验。

## 不能因此关闭的阻塞项

**P0：同步回调中 `IOFramebuffer::stop` 的完整顺序仍未证明。** 即使 `owner` 和 `timer` 的引用均保持有效，也不能自动证明在 IOTimerEventSource action 栈内 `removeEventSource`、`cancelTimeout`、`release`、`IOFramebuffer::stop` 的同步执行始终满足底层 IOKit 协议。R1.2-C 只消除一类对象过早释放窗口，不承诺整个 stop 协议可重入。

**P0：回调目标析构/并发停止。** 回调 `snapshot.target->release()` 或 `unregisterGate` 中释放旧 target 可能触发析构并再入驱动控制流程。重复 stop 的完成语义、等待条件、定时器是否仍在外部的所有权链均待验证。

**P1：运行期 timer 调度失败**、虚拟模式独立采样计时器、power-state 变更和用户态 WindowServer 对 VBL 进度的依赖尚无实际测试。

**系统兼容性阻塞**：`NVAccel` 仍因 NVIDIA 610.57.04 Darwin 生成编译参数缺失无法原生构建，RTX 2050 Ampere Metal 和 Intel 内屏固件格式均没有实机证据。
