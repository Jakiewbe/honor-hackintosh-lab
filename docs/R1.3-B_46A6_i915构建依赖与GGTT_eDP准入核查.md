## 2. 新发现一：PCI `46A6` 匹配路径的源代码证据是成立的，但没有闭合到 NMXGPU 二进制

在单独固定的 FreeBSD drm-kmod 快照中：
1. `pciids.h` 第 671–690 行的 ADL-P 宏**明确包括 `0x46A6`**。
2. `i915_pci.c` 的 `intel_pciidlist` 通过 `INTEL_ADLP_IDS` 指向 `adl_p_info`；`adl_p_info` 的平台类型是 `INTEL_ALDERLAKE_P`、支持 GEN12。
3. `intel_display_device.c` 同样通过 ADL-P 宏绑定 `adl_p_desc`，后者引用 `xe_lpd_display`，包含目标代际显示平台配置。
4. `intel_dp.c` 包含 eDP 及 DP AUX 等实现。**这证明候选 Linux/FreeBSD 源树有相关设备、eDP 与 GGTT 代码，不证明 macOS port 已正确编译、链接、挂载或执行它们。**

具体缺口：NullMoth `gpu-port/xkpi/all-i915.sh` 从开发者机器 `/Volumes/MiniData/build/gpu-src/kpi/drm-kmod` 读取 `Makefile` 和源文件；`cc-i915.sh` 又引用 `freebsd-src` LinuxKPI 以及生成的 `amd.flags`；`kext/build.sh` 消费本地 `obj-i915/*.o`；Intel ID 的关键原始 `pciids.h`、`i915_pci.c`、`intel_display_device.c` 不在 NullMoth 的发布仓库内作为**完整编译输入**。在本轮审查的发布文件中也未找到可锁定这些本地外部树的 Git submodule SHA、完整源码锁定表或已审查的逐对象链接映射。

**P0-BUILD-PROVENANCE 阻塞**：拿到开发者声称“900+274 sources compiled”或一份预构建安装包，并不能替代“精确外部源码 hash + 编译配置 + i915 对象清单 + 符号/链接对应关系”的可复核证明。**也不能仅凭这个缺口声称发布包一定缺失 i915：当前结论是尚未证明，而非已证明缺失。**

## 3. 新发现二：GGTT/扫描缓冲区是独立于 PCI 匹配的关键关口

发布版 [`nmx_fb_bridge.c`](https://github.com/nullmoth/nvidia-macos-driver/blob/1083a98db33a0bb824290556de255f9a95ca5403/gpu-port/xkpi/override/src/nmx_fb_bridge.c#L129-L237) 中：

- `drm_client_modeset_probe` 查找输出，若找不到连接的输出就返回；`drm_client_framebuffer_create` 请求 `XRGB8888` 显示缓冲区。
- `drm_client_buffer_vmap` 获取该 buffer 的 CPU 映射。
- `nmx_xnu_kva_to_phys(va)` 获取第一页 CPU physical address；其后每页须满足 `nmx_xnu_kva_to_phys(va + off) == base + off`，否则打印 **`scan-out buffer is not physically contiguous`** 并退出；随后才调用 `drm_client_modeset_commit`。
- [`nmx_vm.cpp`](https://github.com/nullmoth/nvidia-macos-driver/blob/1083a98db33a0bb824290556de255f9a95ca5403/gpu-port/xkpi/xnu/nmx_vm.cpp#L66-L72) 使用 XNU `pmap_find_phys(kernel_pmap,...)`；[`nmx_fb.cpp`](https://github.com/nullmoth/nvidia-macos-driver/blob/1083a98db33a0bb824290556de255f9a95ca5403/gpu-port/xkpi/xnu/nmx_fb.cpp#L88-L93) 随后把这个物理范围包装为 macOS `IODeviceMemory`。
- 候选 Linux i915 的 `intel_ggtt.c` 管理**设备端图形虚拟地址与映射**。GGTT 连续**本身不保证** WindowServer 能取得 CPU 物理连续的 scanout 映射。

**技术边界**：该检查使用 CPU KVA 的页表物理地址，不直接检查 Intel GGTT page table 条目。若 i915 的 CPU view 是 aperture BAR 等 CPU 物理连续的 I/O 地址映射，检查也可能通过，即使后台实际 RAM 页分散；反过来，一般 `vmap` 成虚拟连续的散页可能失败。不能仅从 GGTT 的一般知识断言这台荣耀必定失败。必须先把 i915 **dumb buffer 创建 → GEM/TTM 对象存储类别 → `vmap` CPU view → XNU physical mapping → macOS aperture ownership** 串起来，确认所用内存的语义、缓存一致性以及清理寿命。

**P0-SCANOUT-MEMORY 阻塞**：没有这条证明，即使 `46A6` probe 与 eDP 模式设置成功，也未必有可用 WindowServer framebuffer。

## 4. eDP 初始化路径的其他 P0 问题

- Linux i915 的 eDP / VBT、DPCD、AUX、电源时序和背光管理在候选 FreeBSD 源树中确有实现；NullMoth 已开发 ACPI 适配 `nmx_platform.cpp`，并在 attach 后调用 DRM client 探测输出。
- 然而移植环境并未提供 **HONOR 实机的 ACPI/VBT、i915 firmware 加载结果、eDP link training、HDCP/显示模式、MMIO/BAR/GGTT 条件**。Linux 源码有这些函数，不意味着 FreeBSD-on-XNU 接口、ACPI 映射或电源时序完整。
- NullMoth `gpu-port/README.md` 仍明示 **`NMXGPU` 尚未在真实 AMD/Intel GPU 上加载**；因此 eDP 接管在报告中只能列为设计路径，不能写成实机内屏可用。
- R1.3-A 已发现的 NMXGPUFB VBL 注销空实现和停机/对象并发风险**继续有效**；本轮不重复建模，只有前述外部源码和扫描映射前置条件获得新证据后，才考虑恢复具体生命周期修复。

## 6. R1.3-C 准入门槛（先取证，后决定是否增加 CI）

1. **外部依赖溯源**：只从上游可公开核对的 `drm-kmod`、`freebsd-src`、`linux-6.14` 来源取得**与 NullMoth v1.14.2 实际构建对应**的 Git SHA/内容散列或等效编译来源清单；找不到则保留 `BUILD-PROVENANCE-BLOCKED`。不能拿本轮单独的 `freebsd/drm-kmod master` 快照冒充开发者实际构建版本。
2. **对象闭合**：确认实际 `srcs-i915.txt`、`amd.flags`、编译结果包含 `i915_pci.c`、`intel_display_device.c`、eDP/AUX 和 GGTT 模块，且有对应构建 manifest/链接结果。**源文件被列入编译清单不等于功能安全。**
3. **buffer 链路**：只读追踪 i915 的 dumb/GEM buffer 物理 backing 和 `nmx_fb_bridge.c` 的连续性要求；指出哪些存储场景可以满足，哪些会失败，不根据抽象 CPU/virtual/physical 地址关系臆测实际结果。
4. **实机证据要求**：如果得到非主力 Intel `8086:46A6` 或同代 Alder Lake-P 的可审计 macOS i915 初始化、EDID/eDP modeset 和实际显示帧的连续日志，再审查下一道生命周期门禁。否则保持 NO-GO。
5. **不触碰主力机**：Windows、分区、BitLocker、EFI、BIOS、kext 安装/签名/加载、第三方安装器均不动。本轮未执行新的 Actions，也没有做原生 GPU 编译测试。

## 7. 阶段决策

**研究主轴没有转移**：目标依然是“荣耀 GLO-FX6P 的 Intel 内屏在 macOS 获得真实、可靠的显示能力”。代码匹配已具备足够静态支持；**真正阻碍下一步的是公开驱动移植的构建来源闭合与 scanout buffer 语义**。在这两个前置条件明确前，不继续堆叠 VBL/Metal 补丁，不为绿色 CI 而重复现有测试。

**`R1.3-B SOURCE-MAPPING DONE / BUILD-PROVENANCE-BLOCKED / SCANOUT-MAPPING-UNVERIFIED / RUNTIME-NO-GO`**。
