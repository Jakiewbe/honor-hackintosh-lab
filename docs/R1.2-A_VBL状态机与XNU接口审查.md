## 1. 真实源码中的问题

在 `kexts/NMIntelFB/intelfb.cpp` 中：

1. 第 89 行 `volatile bool fStopping` 不是并发同步机制。
2. 第 90–98 行 VBL 定时回调直接读取 `fVbl.proc/target/ref` 并在回调末尾用 `thread_call_enter_delayed` 给同一任务重排队。
3. 第 99–102 行 `armVbl()` 没有向调用方返回分配/调度失败状态，失败后仍可继续发布显示服务。
4. 第 171–180 行 `registerForInterruptType()` 直接覆盖回调结构，`unregisterInterrupt()` 无条件返回成功但并未注销目标。
5. 第 353–362 行 `stop()` 设置 `volatile` 停止标志后调用 `thread_call_cancel/free` 循环；没有与回调读取、注册、注销共用的序列化机制。

Apple XNU [thread_call.h](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/thread_call.h) 明确说明：从定时回调内部调用 `thread_call_enter_delayed` 重排队，**可能产生多个同时进行的回调调用**。同一文件也说明 `thread_call_cancel` 不等待已开始的调用，`thread_call_free` 的“pending”语义不能替代完整的回调生命周期证明。

## 2. 选择 IOTimerEventSource 的依据与限制

Apple XNU 的 [IOTimerEventSource.cpp](https://github.com/apple-oss-distributions/xnu/blob/main/iokit/Kernel/IOTimerEventSource.cpp) 在超时路径中使用 `IOWorkLoop::closeGate()` 调用目标 action；[IOWorkLoop.cpp](https://github.com/apple-oss-distributions/xnu/blob/main/iokit/Kernel/IOWorkLoop.cpp) 采用**可重入锁**，允许回调内合法的注册/注销递归，但也意味着必须审查停止/释放中的再入。

`IOTimerEventSource` 提供 `setTimeoutUS`/`cancelTimeout`/`disable` 等公开 IOKit API，其内部处理 thread-call 生命周期；候选修复优先使用它，而不是直接调用第三方 kext 未确认导出的 `thread_call_cancel_wait`。**这并不自动证明安全**：必须验证定时回调与 `stop()`、`removeEventSource()`、`release()` 的锁顺序，特别是 **stop 在定时器自身回调中被再入调用**的情况。

## 3. 提议的状态机与不能放宽的性质

| 状态 | 意义 | 允许操作 |
|---|---|---|
| NEW | 对象尚未成功取得定时源 | 仅初始化、尝试 arm |
| ARMED | timer 已分配、挂入 workloop 且已调度 | 在同一 gate 注册、注销、发出回调、重排队 |
| STOPPING | 已禁止再注册和重排队，等待当前回调结束 | drain / release，不再投递新任务 |
| DRAINED | 当前回调结束、事件源解绑且引用释放 | 禁止重新 arm、禁止旧目标回调 |
| REJECTED | timer 创建/加入/调度失败 | fail-closed，不宣称显示控制器启动成功 |

**必须满足：**

- 定时回调开始时固定其目标快照，而不是在过程中使用可能新注册的回调目标。
- `unregisterInterrupt` 从其它线程调用时，只有在已持有或获取 gate 并与当前回调串行化之后，才能确认注销完成。
- 当 `unregisterInterrupt` 在当前回调中**再入**时，允许清除后续回调目标，但绝不在持有外部对象指针后进行异步使用。
- `stop()` 从其它线程调用时，先阻止重排队，再取消计时、移除事件源、释放引用；不应在持有 gate 时调用可能等待活跃回调的取消方法。
- **stop 在回调中再入**的资源释放顺序尚未形成可信协议，因此此用例必须在候选代码阶段单独通过故障注入和源码审查，模型 **不覆盖也不证明**它。
- timer 分配、事件源加入或首次调度失败必须阻止驱动对外发布成功，并清理半初始化资源。
- 虚拟显示构建 `NMINTELFB_VIRTUAL` 也存在第二个采样用 `IOTimerEventSource`，两个事件源的清理不能互相覆盖。

**模型假设 workloop gate 能实现完全串行化；它没有实际执行 XNU 内核、IOFramebuffer 外部回调或任何设备，也没有验证回调销毁的引用计数。** 模型通过只说明在给定假设下，参考状态转换未违反所列断言，不能说明内核补丁已经修好。

## 5. R1.2-B 候选补丁准入

在形成源码补丁前，尚须解决：

1. `IOFramebuffer::start()` 之前与之后 timer 创建的正确时序。当前 `armVbl` 在 `IOFramebuffer::start()` 之后调用，失败回退需保证 super class 半启动状态被正确清理。
2. 回调内同步执行 `stop()`、`unregisterInterrupt()` 的再入与事件源释放语义；必要时需要单独的 deferred teardown 阶段，而非在当前 action 栈上释放 sender。
3. 系统级 `setInterruptState` 应明确处理 enable/disable，不能继续无条件报告成功但不执行。
4. 编译目标应固定 x86_64、Xcode 16、macOS 15.5 SDK；先独立最小编译、再对**叠加 R1.1 的临时源码副本**编译、链接并检查符号。
5. 任何未能证明所有权或停止完成的分支要**停止/返回错误**，不可继续发布显示服务；不能靠在主力 Windows 设备上加载来“看看会不会崩”。
