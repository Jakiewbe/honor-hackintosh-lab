## 1. 新证据：为何存在潜在的 ABBA 死锁

| 路径 | 从公开源码直接可见的行为 | 证据 |
|---|---|---|
| Apple IOGraphics `IOFramebuffer::stop` | 函数开始先创建 `SYSGATEGUARD(sysgated)`，紧接着 `FBGATEGUARD(ctrlgated, this)`，即先请求 **SYS**，再请求 **FB** | [IOFramebuffer.cpp 第 4409–4415 行](https://github.com/apple-oss-distributions/IOGraphics/blob/main/IOGraphicsFamily/IOFramebuffer.cpp#L4409-L4415)，该源码文件的 Git blob SHA `8a6e82c2c48dfe410ff2d19f67e466c2c137ce6b` |
| 同文件的门锁宏 | `SYSGATEGUARD` 指向 `gIOFBSystemWorkLoop`；`FBGATEGUARD` 指向 `FBWL(fb)=fb->__private->controller->fWl`，是**两个不同的 workloop 门锁** | [IOFramebuffer.cpp 第 1125–1160 行](https://github.com/apple-oss-distributions/IOGraphics/blob/main/IOGraphicsFamily/IOFramebuffer.cpp#L1125-L1160) |
| Apple XNU 定时器回调 | `IOTimerEventSource::timeoutAndRelease` 获取 timer 所在 workloop 的 gate 后直接执行其 action | [IOTimerEventSource.cpp 第 165–193 行](https://github.com/apple-oss-distributions/xnu/blob/main/iokit/Kernel/IOTimerEventSource.cpp#L165-L193) |
| XNU `IOWorkLoop::runAction` | `closeGate()` 后同步执行 action；workloop 的 gate 是递归的，但只能消除**同一把门锁**的重复加锁，不能消除不同锁之间的循环等待 | [IOWorkLoop.cpp 第 565–578 行](https://github.com/apple-oss-distributions/xnu/blob/main/iokit/Kernel/IOWorkLoop.cpp#L565-L578) |
| R1.2-C 候选 VBL | `vblFire` 在 timer action 栈中调用外部 `snapshot.proc(...)`，此时控制器 FB 门锁尚未释放；后续才归还 owner 和 sender 的 retain | [R1.2-C 补丁](../patches/r12c_vbl_callback_lifetime.patch) |
| NMIntelFB 停止实现 | `NMIntelFB::stop` 先 `disarmVbl()`，最后仍然同步调用 `IOFramebuffer::stop(provider)`；没有在可能已持有 FB gate 的情况下改道至不持锁的停止上下文 | [R1.2-B 补丁](../patches/r12b_vbl_workloop_gate.patch) |

**严格的锁顺序反例（条件性，不是实测）：**

```text
Thread A: VBL timer action
  acquire FB
  call snapshot.proc(...)
  external callback synchronously calls NMIntelFB::stop(...)
  tries to enter IOFramebuffer::stop: acquire SYS  [BLOCKED: B owns SYS]

Thread B: concurrent system-side stop
  acquire SYS
  tries to acquire FB                  [BLOCKED: A owns FB]

Wait-for cycle: A -> B -> A
```

由此可以证明：**以现有公开实现所显示的锁顺序为前提，这条外部回调→同步 stop 路径没有普适的无死锁保证**。只有并发执行、回调确实触发同步停止、以及系统停止线程以该顺序取得门锁等条件同时满足才构成此反例。并没有观察到这台 HONOR 的真实死锁。

**版本限定非常重要：** 这里读取的是 Apple 公开的 IOGraphics 与 XNU GitHub 源码及其上述文件 hash；它们不必然与 macOS 15.5 安装的所有私有/发布二进制逐版一致。实际目标内核、IOGraphicsFamily 版本和符号/锁行为没有通过运行时或二进制核验。该问题的实机发生概率未知，不能据此断言“一定死锁”。

## 2. 第二风险：外部对象析构带来的隐式反向加锁

R1.2-B 的 `unregisterGate` 与 `stopGate` 会在控制器 gate 内清空回调槽并直接调用 `previous->release()`。引用计数减至零时，外部对象的 `free()` 或后续清理可能反向调用 framebuffer 的控制方法；如果该回调间接进行同步 `stop`，就可能再次从 **FB→SYS** 请求锁。

R1.2-C 在 VBL 回调内给 `owner` 和 `timer` 追加了引用，能保护当前回调返回后的一部分访问；**不会改变门锁顺序，也不保证外部 target 析构不会触发同步停止**。

不能简单把 `unregisterInterrupt` 改成不加锁或移除引用计数：这样可能重新引入 target UAF。需要隔离**改写 callback 槽位（必须串行化）**与**最终释放外部对象（应在恰当的无门锁上下文）**两段操作。

## 3. 关于 cancelTimeout 的反误判

XNU 公开的 `IOTimerEventSource::timerEventSource(owner,action)` 默认采用 `kIOTimerEventSourceOptionsPriorityKernelHigh`，内部是 **passive timer** 路径。该路径的 `cancelTimeout` 使用 `thread_call_cancel`，不是无条件调用 `thread_call_cancel_wait`。因此不能把本阶段潜在死锁直接归咎于“timer cancel_wait 自等待”；真正新增的证据是 **IOFramebuffer::stop 的 SYS→FB 与 VBL 回调上下文的 FB→SYS 反向加锁**。

## 4. 修复架构候选：两阶段 quiesce/finalize

**以下是设计要求，不是已实现代码、不是证明可部署的修复。**

1. **回调阶段（FB gate 内）**：只允许取快照/调用已固定寿命的监听者、标记 `STOP_REQUESTED`、阻止未来的 VBL 重排队。绝不在该回调栈同步执行 `IOFramebuffer::stop`，也不直接做可能反向取得 SYS gate 的最终资源销毁。
2. **Quiesce（在 FB gate 内短操作）**：让当前监听者不会被新的回调取到；需要让旧 target 的最后一个 `release()` 发生在已退出敏感 gate 的安全上下文。必须考虑 target=owner、嵌套 unregister、停止与 VBL action 交错。
3. **Finalize（外部生命周期执行器）**：先让 VBL action 退出并释放 FB gate，随后由一个只执行一次的、具有稳定 owner 引用的外部执行器请求标准停止路径，遵守 **SYS→FB** 的系统既有锁顺序。单纯将任务放入同一 FB workloop 并不自动满足要求。
4. **引用平衡/退出**：对 owner、sender、callback target、deferred work 各自证明 acquire/release 次数及销毁责任；当最终停止等待无法证明有界完成时维持 NO-GO，不能通过无限循环重试或忽略错误实现所谓“修复”。
5. **拒绝不可信同步入口**：如果 IOKit 可能在同步回调链上直接调用 `stop`，必须额外证明上层请求可以合法延后且不会违背 `IOService::stop` 语义，**否则停止进行运行时实验**，不能在 `stop` 内直接 `return` 伪称清理成功。
