## 2. R1.2 核心审计发现

原版 [NMIntelFB/intelfb.cpp](https://github.com/nullmoth/nvidia-macos-driver/blob/0960b2ef5dbc4a573056d4c8e042a5bd2e15d651/kexts/NMIntelFB/intelfb.cpp)：

- 第 89–102 行，`fStopping` 是普通 `volatile bool`，`vblFire` 读取 `fVbl.proc/target/ref`，没有与注册/注销统一的同步协议，且自动为同一个 thread call 重排队。
- 第 172–180 行，`registerForInterruptType` 直接覆盖回调结构；`unregisterInterrupt` 无条件报告成功却没有清空回调或阻止已排队的调用。
- 第 353–362 行，`stop` 使用 cancel/free 重试循环收尾，但**没有**为该回调注册状态、目标对象所有权和 `unregister` 返回后不再调用提供单独证明。
- 第 99–102、319–321、347–350 行，`armVbl()` 返回 `void`。分配 timer 失败时只打日志，`start()` 仍可报告成功（需同时考虑虚拟和实体显示模式）。
- 同一上游 `NVAccel` 的异步 flip 入口在 R1.1 候选被关闭；全局旧回调实现及其它生命周期路径仍未完全重构。

Apple XNU [`thread_call.h`](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/thread_call.h) 中有 `thread_call_cancel_wait` **声明**，但公开 [`config/Mach.exports`](https://github.com/apple-oss-distributions/xnu/blob/main/config/Mach.exports) 列有 `_thread_call_cancel`、`_thread_call_free` 等，而**不列** `_thread_call_cancel_wait`。因此不能仅凭函数在头文件里出现，就假设第三方 macOS kext 能调用并成功链接。此项尚需按对应 SDK 和内核导出表逐版确认。

## 3. R1.2 修复的必过契约

1. **状态机**：明确 `Uninitialized → Armed → Stopping → Drained`，并定义 start 半途失败时回退操作；不能只替换 `volatile`。
2. **唯一同步协议**：注册、注销、定时回调取出目标、递增/递减 in-flight 以及进入 stop 的状态转换需要统一协调；不能在持有不可重入自旋锁时调用不可信外部回调。
3. **对象寿命**：回调的 target、ref 的所有权及回调过程中 `unregisterInterrupt` 的同步返回语义需明确；必须分析从回调线程本身调用 unregister 的死锁场景。
4. **终止条件**：`unregisterInterrupt` 不能在旧回调仍可执行时谎报已经注销。停止后不允许新的重排队；不能出现循环无限等待、用后释放或任意 target 指针的晚到回调。
5. **定时器分配失败必须 fail-closed**：除非可以证明没有 VBL 也仍能安全显示，否则拒绝发布已就绪显示服务并按 reverse order 清理。
6. **真实 API 验证**：只用确实可在 Intel macOS 15.5 kext 构建环境中使用的导出符号；先做离线并发测试、源码审查，再做只编译不加载的 CI。
7. **旧版异步路径隔离**：保持 R1.1 对 `nvAccelIopAsyncStart` 的主动调用禁用，直至具备独立的 lifetime 证明。
