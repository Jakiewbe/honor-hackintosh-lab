# 驱动开发可行性与分阶段计划

## 当前范围与完成标准

用户已关机，最新授权是先调研“是否可以尝试自主开发和适配驱动”。本轮只做源码、构建条件与研发路线评估，不开始新的驱动实现、不触发 CI、不要求开机采集、不安装或加载内核组件。上一轮 candidate 仅保留为静态研究材料。

完成标准：给出有原始来源的路线比较、明确的代码入口与缺口、可证伪的首阶段目标、原生构建要求、后续实机验收和退出条件。研究结论不能冒充驱动完成。

## 结论与证据变化

**可以尝试实验性适配，有现成代码和已确认的内屏输出作为研究起点；目前不能保证完成，更不能把它当成装几个驱动包即可修复的任务。**

基于当前材料，优先候选为 RTX2050 渲染 + Intel 内屏桥接。这是研发判断，前提是 RTX2050 的实际 RM/GSP/Metal 可运行，以及 Intel 显示面的地址、模式和同步合同能得到验证；两项目前都没有本机证据。

现状与历史资料必须区分：

- 现在用户已实际进入恢复、安装、首次设置和正式桌面，内屏报告 2160×1440。不能继续把旧文档的“未进入 macOS/未显示桌面”当作当前事实。
- 两块显卡报告均为 No Kext Loaded；没有本机 Metal 渲染或 GPU 加速验收。旧资料中的“没有自主驱动实机验证”仍成立。
- 无外接显示器，不能依赖独显外接输出完成本轮目标。MUX 物理存在与有效切换仍未知。
- 旧 NMIntelFB 曾完成原生 real/virtual 编译和 kext 静态链接；回调重入、SYS→FB 锁序与停止同步风险没有因此解决。复用 R1.2-C/D/G 记录，不重跑同质模型或重新堆叠旧 VBL 补丁。
- 当前本地仓库为带既有修改的历史分支；本轮不切换、不重置、不更改其旧治理目标，研究结果独立保存在 H4-gpu-audit。

## 路线比较

| 路线 | 有什么真实起点 | 主要缺口 | 本轮判断 |
|---|---|---|---|
| RTX2050 渲染 → NMIntelFB 内屏桥接 | NVIDIA 25A9 已在设备表；NVAccel 有 head 4 的 Intel 面复制分支；NMIntelFB 有 46A6/display version 13 | 本机 GSP/Metal；安全接管 Intel 显示面；WindowServer 关联；同步与停止；当前发布包没有安装桥接 | 最值得先做有限可行性试验，尚不进入部署 |
| Intel NMXGPU/i915 + ANV + Metal 插件 | 上游 gpu-port 有 Darwin DRM/LinuxKPI、i915、ANV、NMXAccel 源码；本仓库有独立 i915 调用图与接口合同 | 上游没有对应物理加载验收；完整构建输入/对象追溯；DMA、PM、IRQ、GEM/GGTT、显示桥接与模式切换 | 独立研究备选，工程面更大，不能用 nmxintel=1 代替开发 |
| 将 WhateverXe 适配到 46A6/Sequoia/内屏 | 当前有 Tiger Lake 与 Alder Lake-N 的 Apple 驱动适配后端 | 当前目标 Big Sur 20G1443；46A6 不在已实现后端中；内屏和 Alder Lake H/P/U 仍在规划 | 暂不作为本机首选，不重装系统去试未覆盖的组合 |
| 从零写完整 Intel Metal 驱动 | Intel/Linux/Mesa 的硬件与渲染资料可研究 | 新 macOS 内核接口、命令提交、内存管理、编译器、Metal/IOSurface/媒体/电源整栈 | 范围最大，不适合作为第一工作包 |

上游 v1.15.0 的“Intel 承载的内屏不加速”是明确发布边界。NVIDIA headless Metal 可让应用选择第二个 GPU，但其代码刻意让 WindowServer 留在拥有显示输出的 GPU；不能据 Metal 标签推导桌面得到加速。

## 优先路线的实际代码入口

固定 NVIDIA 主线：cd8e2bb04da48d2fa70cf1895879608f3588dbfb。

| 环节 | 真实代码 | 已证明与未证明 |
|---|---|---|
| RTX2050 枚举 | app/Resources/nvidia_gsp_ids.json，25A9 | 表项存在；并非 GPU 初始化成功 |
| Intel 模式接管 | kexts/NMIntelFB/intelfb.cpp：probe、adoptFirmwareMode、start | 读活动 plane/stride/format，映射 BAR0/BAR2；本机状态与映射正确性未知 |
| 显示面通信 | 两份 nvrm_vram_abi.h，NVRMVramRequest/nvScanoutInfo | 当前源码两份头字节一致、ABI_VERSION=2；尚未核对实际发布二进制和原生编译布局 |
| WindowServer 关联 | kexts/NVRM/accel/nvrm-accel.cpp：fbPublished、registerFramebuffer、askFramebufferForScanout | 找 NMIntelFB，使用 index 4；gNvIgpu 默认 0，实验路径未由此证明可运行 |
| 完成的画面写往内屏 | NVDisplayPipe 的 CPU-only scanout 分支与 performTransaction | 当前有复制路径，仍须证明 GPU completion、像素格式、边界、CPU 缓存与帧节拍 |
| 内屏保护 | NVRMFBClaim 的匹配 personality | 已有仅匹配 NVIDIA 主厂商/显示类的本地候选，6项静态检查通过；不是加速修复 |
| 生命周期 | NMIntelFB 的 VBL/interrupt/stop；IOGraphics/XNU 调用责任 | 既有审查未关闭锁序/回调重入风险，当前不能部署 |

这里最关键的不是再增加 PCI ID，而是把“GPU 已经画完的帧”安全交给“当前实际被面板扫描的显示内存”，同时让 macOS 正确关联加速器与内屏。

## 必须优先解决的工程问题

1. **显示内存不是随便一个物理地址。** 当前代码 fSurf 是 GGTT 偏移，BAR2 是 CPU 可访问的显存窗口；必须验证其对应关系、映射范围、pitch、格式与缓存属性。不把 BIOS stolen 基址、GGTT 0、当前画面地址混为一谈。
2. **完成顺序必须真实。** command buffer 已提交不等于 GPU 已完成。复制前需有效完成信号；失败、超时和设备重置必须传播，不能显示半帧后报成功。
3. **刷新和停止必须可控。** 当前 adoptFirmwareMode 的计数无效时 60Hz默认值、定时器模拟 VBL，以及 stop 中等待线程释放，不能作为实机时序/安全证明。先闭合真实锁序、引用与注销责任，再讨论实现；不重新补丁叠补丁。
4. **固定硬件状态仅适合受限原型。** 首阶段可以研究保留固件当前点亮的模式，但这只覆盖初始桌面。模式切换、睡眠恢复、背光与 GPU 重置需要独立实现及验收，不把固定模式原型当作完整驱动。
5. **RTX2050 必须独立验收。** 设备 ID 在表里不代表 GSP 初始化、NVK、Metal 或驱动供电已通过。未通过此关时应停止混合桥接，重新评估 Intel 独立路线。

## 成本的一个可计算边界

目前屏幕分辨率 2160×1440，按每像素 4 字节计算：

- 一帧：2160 × 1440 × 4 = 12,441,600 字节。
- **若**刷新率为 60Hz：12,441,600 × 60 = 746,496,000 字节/秒，约 0.746GB/s 的单次全帧复制量。

60Hz 是情景计算，不是已测到的刷新率。GPU读回、额外复制和同步可能进一步增加成本。仅有足够带宽不能证明低延迟、无撕裂或流畅桌面，因此先测端到端帧完成和 CPU 负载，不承诺帧率或成功概率。

## 开发环境和可复现性

- 当前 Windows 可以继续做源码审查、版本锁、接口整理和有限离线测试。
- 原生对象/kext 链接、Apple kernel collection 的符号校验需要可用的 macOS 构建环境、对应 SDK/Kernel.framework/工具链。此前工作流实际使用 xcrun clang++；本轮没有新建或触发 CI，也没有完成新的原生编译。
- 将来已安装的 macOS 可作为构建环境候选，但其实际构建号、工具链、SDK、恢复能力仍需核对；不要求现在开机，也不要求另买 Mac。
- 当前 accel_build.sh 还读取外部 OGKM 的 `_out/Darwin_x86_64/compile_cmds.sh`。在所读主线树中没有提供该生成文件，也没有找到以该文件名命名的生成入口。这是构建输入追溯缺口，不能证明不存在其他外部生成方式。不能捏造 flags 或以旧对象凑链接。
- NMIntelFB 的窄桥接可以研究独立构建，但必须与实际 NVAccel 通信 ABI 对齐。旧版本 BUILD-PASS 不能替代新源码/SDK/二进制组合的验证。
- 所读 NullMoth 主许可证为 PolyForm Noncommercial，其他模块各有许可；开发前需保留来源/许可台账，不把“公开可读源码”当作默认任意商用或重分发授权。本报告不作商业授权法律结论。

## 若后续批准开发，推荐阶段

| 阶段 | 工作范围 | 通过条件 | 停止条件 |
|---|---|---|---|
| A：源码与合同收敛 | 只围绕 46A6/25A9、模式接管、显示面通信、复制、停止路径，复用既有研究 | 版本/许可/直接依赖明确；没有未实现却报成功的必需环节；源→对象有可审查方案 | 生成输入/SDK/ABI或关键生命周期无法闭合 |
| B：原生编译与受控软件验证 | 新的独立候选副本、静态链接、布局、失败退出与像素复制边界验证 | 无缺源/强符号不明；真实代码的边界与错误可验证 | 只靠模型/字符串/预编译旧对象才能通过 |
| C：硬件信息与恢复准备 | 开机后再设计最小只读采集、独立保存当前成功引导和系统恢复证据 | 本次真实 framebuffer、BAR/plane/映射、系统版本与退出方式明确 | 仍需猜 MMIO地址、显示归属或安全恢复方式 |
| D：RTX2050 渲染验证 | 单独验证 RM/GSP、NVK、Metal 真实像素结果 | GPU工作/错误/完成有日志和输出证据，保留可用内屏 | 初始化或像素结果失败，内屏不可恢复 |
| E：当前模式内屏桥接 | 一个显示模式，逐帧复制及受控停止 | 内屏持续刷新，窗口交互改善，像素正确、无新崩溃，恢复验证通过 | Metal 标签存在但画面不更新、锁死或错误被忽略 |
| F：完整使用能力 | 另行处理模式切换、背光、睡眠、重启与稳定性 | 每项有独立实际结果 | 任一能力仅源码声明或理论预测 |

A/B 是未来开发建议，不表示已获准现在实施；C/D/E涉及实机且需要单独确定具体范围。本轮只完成研究规划。

## 自检与本轮边界

先查 Bug：完整 Metal 不由 PCI ID/设备名/头文件一致性证明；应用 Metal不等于 WindowServer 内屏加速；虚拟面板不等于物理面板；旧对象编译不等于新版本构建；地图上的源文件不等于依赖闭包。

再检查更简单路径：先做窄范围 NVIDIA渲染到既有内屏的实验可行性，保留 Intel独立路线作为对照，不同时启动整个 i915/Metal 重写。

本轮没有修改 EFI/BIOS/Windows/macOS，没有开机采集、安装/加载/签名驱动、执行 GPU寄存器访问、启动CI、公开消息、提交或推送。结果是研发可行性判断与分阶段建议，不是可部署驱动。
