# RTX 2050 在本机 macOS 上的可行性与止损判断（2026-10-18）

状态：**SOURCE-REVIEW + 构建/链接证据**。没有任何 GPU 运行证据。本文件回答"继续投入还是止损"，不回答"能不能加速"。

## 2. 未证实的（全部需要实机）

1. RM 能否在这块 GA107 上完成 `rm_init_adapter` / GSP 启动（ID 在支持表里只代表有代码路径）。
2. GSP 固件来源与版本匹配（未审查、未下载）。
3. `allocateDevice()` 在本机能否成功（`getDisplays()` 无显示器时我们已知会失败，这正是 R10/R11 处理的路径）。
4. VRAM/DMA/IOMapper 真实映射与 GPUVA。
5. Metal 渲染服务与像素读回。
6. NVIDIA→Intel 内屏桥接（上游已拒绝非 head 0 成为主 framebuffer）。

## 3. 核心风险：NVRM.kext 无法用公开源码重建

R13 的量化结果：`kexts/NVRM/` 全部 9 个根 C++ TU 编译并链接后是 **361,768 B / 649 导出符号**，而发行版是
**16,787,920 B / 34,302 符号**，覆盖率约 **2%**；仓库内没有任何预编译对象。结论：NVRM.kext 的绝大部分输入不在
公开树里（最可能是 OGKM `nvidia-modeset` 核心被私有构建一起编进去）。

这带来一个绕不开的判断：

- 要走到 `GPU-RUNTIME`，**必须安装上游预编译的 NVRM.kext**；
- 但项目规则明确：**来源不明确的预编译驱动不得视为可信构建产物**；
- 我们目前能提供可信构建证据的只有 NVAccel 与 NVRMFB 两个 kext，而它们**依赖** NVRM 提供 RM/KAPI。

也就是说：**验证 GPU 的那一步，必然要用一个我们没有构建证据的二进制**。这不是技术细节，是这条路线当前的根本约束。

## 4. 结论（分三档，不含"加速成功"这一档）

**A. 可以继续（有条件）**：如果用户接受"用上游预编译 NVRM 做一次隔离实机实验"，并且满足：
- 独立外接 SSD、可完整回退（移除 kext / 从备份恢复）；
- 每次安装/加载都单独授权，且先记录现有可启动状态；
- 目标是**采集证据**（`kprintf` 中出现 RM/GSP 初始化结果、`debug.nvrm_kms_close_deferred`、IORegistry 状态），
  不是"让桌面变快"。

**B. 应当止损**：如果用户不接受使用无构建证据的 NVRM，或不接受实机加载 kext——那么以现有公开材料，
RTX 2050 的 macOS 加速**无法在本项目内被验证**，应明确记为"不可验证"，不再增加离线补丁。

**C. 完全止损**：如果 A 条件下的实验显示 RM/GSP 在本机无法完成初始化（例如 `rm_init_adapter` 持续失败、
GSP 无法启动），则按任务书要求给出技术止损结论，停止 NVIDIA 方向，把 Intel 内屏做到"基本可用"为止。

## 5. 我的建议

先做 **A 的最小版本**：一次隔离的 `KEXT-LOAD` 取证实验（只加载，不做内屏桥接、不改 EFI/SIP），
用 `NVAccel`/`NVRMFB` 我们自己的构建物 + 上游 NVRM，采集日志后立即回退。
如果这一步拿不到 RM/GSP 的正面证据，就执行 C，而不是继续写第 13 个补丁。

## 6. 不做什么

- 不为了让 GPU "看起来工作"而伪造 DMA/VRAM/固件返回值；
- 不把 NVIDIA framebuffer 强设到 Intel 内屏；
- 不在没有回退方案的情况下改动现有可启动系统。
