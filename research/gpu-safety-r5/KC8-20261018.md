## 三十六、471/472 的两处差异已归因（R83）

### _panic 来自我们自己新增的 TU，不是上游代码

esearch/gpu-safety-r5/darwin/nvlink_locks.cpp:19：

`cpp
[[noreturn]] void lockFailure(const char *operation, kern_return_t status)
{
    // The upstream void API cannot propagate failure. Never return without
    // acquiring the permit, or pretend that a failed signal/destroy succeeded.
    panic("HONOR G1 NVLink lock invariant: %s failed (%d)", operation, status);
}
`

该文件是**独立附加 TU**，被 	ools/g1_full_build.py 编入候选 kext（见 NVLINK-DARWIN-LOCKS-20261018.md：
"候选路径：esearch/gpu-safety-r5/darwin/nvlink_locks.cpp 独立附加 TU"）。

所以：候选构建比发行版多出的 _panic 导入，**原因是我们自己的 NVLink 锁实现选择在不变式失败时 panic**
（因为上游 oid 接口无法传播失败——这正是 P0-4 的同一根因）。

### IOUserClient::free 来自发行版的用户客户端类

候选树的 kexts/NVRM/accel/iofam/IOAccelSurface.h、IOAccelSubmitter2.h 定义了
class IOAccelSurface : public IOUserClient 等，但这些 TU **没有编进 9 单元链接**；
发行版有完整的 IOAccel 用户客户端，因此导入 IOUserClient::free。

## 结论

471/472 的一致 + 2 处可解释的差异，说明：

1. 审计的 472 项清单确实是**真实驱动导入面**，不是构造出来的；
2. 差异全部来自**我们这边多一个 panic、少一组 IOAccel 用户客户端**，方向明确；
3. 这也顺带把 P0-4（oid 接口不可传播）在**符号层面**显形了：我们没有静默忽略失败，
   而是升级成 panic——这是"不假装成功"，但也不是"能优雅传播"。
