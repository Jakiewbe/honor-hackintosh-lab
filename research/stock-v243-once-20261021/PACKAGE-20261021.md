## 接手后的门禁修复与真实依赖结果（2026-10-21）

此前三次整包门禁（39533781713 / 39535081198 / 39536854715）都卡在检查器自身，而不是候选源码。
逐条修掉后，审计第一次跑到了「导入归因」这一步。

### 1. 三个检查器缺陷（都不是放宽语义）

| 现象 | 真因 | 修法 |
|---|---|---|
| `function/data section kind differs` | 解析器只把 `metaClassE` 当作 data，vtable/typeinfo/C 全局变量都被判成函数；且 `gMetaClassE` 是大写 M | 按 `__ZTV/__ZTI/__ZTS/__ZTT`、`_g*`、`*MetaClassE` 判 data；不匹配只记录 `kind_matches_role`，不再中止 |
| `duplicate selected symbol in member` | 一个 KC member 里同名符号可以出现多次（局部/外部条目、多视图副本） | 按 `(name,value)` 去重，记录 `duplicates_removed`；同名不同值记 `ambiguous_values` |
| `IOGraphicsFamily.kext/.../Info.plist` 不存在 | macOS 15 把 IOGraphicsFamily / IOAcceleratorFamily2 / IOSurface 放进内核集合，磁盘上没有对应 kext 目录 | 定义从 KC 观察；版本兼容性标 `UNVERIFIED_NO_DISK_INFO_PLIST`，不编造版本号 |

### 2. 修好后的真实归因（run 39544753829 / `ba7c364`）

| 组件 | 导入数 | 已归因 | 仅有局部定义（导出未验证） | 完全找不到定义 |
|---|---|---|---|---|
| NVRM | 478 | 478 | 0 | **0** |
| NVRMFB | 478 | 478 | 0 | **0** |
| NVAccel | 884 | 843 | 34 | **7** |

7 个完全找不到定义的符号：

```
__ZN14IOAccelSurface20surface_lock_optionsEjjP25IOAccelSurfaceInformationy
__ZN14IOAccelSurface22surface_unlock_optionsEjj
__ZN14IOAccelSurface28set_shape_backing_length_extEjjyjyP19IOAccelDeviceRegiony
__ZN14IOAccelSurface9set_shapeEjjP19IOAccelDeviceRegiony
__ZN17IOAccelGLContext211processSwapEj
__ZN24IOAccelLegacyDisplayPipe9setStereoEj
__ZN27IOAccelLegacyDisplayMachine9setStereoEjj
```

### 3. 这 7 个符号为什么会出现（已定位到源码）

- 它们由仓库里**重建的 IOFamily 头文件**声明为普通虚函数：
  `kexts/NVRM/accel/iofam/IOAccelSurface.h:36-39`、`IOAccelGLContext2.h:20`、
  `IOAccelLegacyDisplayPipe.h:16`、`IOAccelLegacyDisplayMachine.h:23`。
- `kexts/NVRM/accel/tahoe_fwd.h` 自己写着「GENERATED ... for the macOS 26 (Tahoe) build」并在
  `#ifdef NM_TAHOE` 下；但上面几个 `iofam/*.h` 的声明**没有**条件编译。
- `nvrm-accel.cpp` 里这 7 个方法名**一次都没有出现**，即 `NVSurface`/`NVGLContext` 等派生类没有 override；
  派生类 vtable 需要基类实现地址 → 变成导入符号。
- macOS 15.7.9 的 `IOAcceleratorFamily2` 里这 7 个名字在 KC 记录和 kernel nm 里都不存在。

结论：**重建的 IOAccel 类布局是 Tahoe（macOS 26）的，不是 15.7.9 的**。用它编出来的 NVAccel
在 15.7.9 上缺 7 个基类符号，不能声称可加载。这是 NVAccel 的问题，不是 NVRM/NVRMFB 的；
后两者 478 个导入全部有提供者。

门禁仍以 FAIL 结束（fail-closed），失败理由现在是真实的依赖缺口，而不是检查器误报。

### 4. 状态

- NVRM / NVRMFB：导入 478/478 已归因；`kext_load=NO_GO`、`gpu=NOT_RUN` 不变。
- NVAccel：34 个局部定义（导出未验证）+ 7 个缺失，属于 macOS 15 兼容性问题，需要单独决定
  是改用 15.x 的类布局还是补 override；本轮不擅自改加速器语义。


## 采用方案 1 后：三组件静态门禁通过（run 39549098741 / `98ab736`）

方案 1 = 把 macOS 26 才有的 7 个 IOAccel 虚函数从 15 构建里排除，让 NVAccel 不再导入
15.7.9 不提供的符号。

实现：`research/stock-v243-offscreen-20261021/iofam-macos15-layout.patch`
（SHA256 `c85196277c1d980d…`），把下列声明包进 `#ifdef NM_TAHOE`：

| 头文件 | 声明 |
|---|---|
| `kexts/NVRM/accel/iofam/IOAccelSurface.h` | `set_shape`、`set_shape_backing_length_ext`、`surface_lock_options`、`surface_unlock_options` |
| `kexts/NVRM/accel/iofam/IOAccelGLContext2.h` | `processSwap` |
| `kexts/NVRM/accel/iofam/IOAccelLegacyDisplayPipe.h` | `setStereo` |
| `kexts/NVRM/accel/iofam/IOAccelLegacyDisplayMachine.h` | `setStereo` |

补丁只在整包步骤里、内部链接之后应用（内部链接 preflight 要求干净固定输入），
应用前用 lock 校验哈希，并在报告里记录 `iofam_overlay`。

### 结果

| 组件 | 导入 | 已归因 | 未解析 | 仅有局部定义 |
|---|---|---|---|---|
| NVRM | 478 | 478 | **0** | 0 |
| NVRMFB | 478 | 478 | **0** | 0 |
| NVAccel | **877**（原 884） | 877 | **0** | 34 |

状态字符串：`PASS_STATIC_KERNEL_BUNDLES_NOT_LOADER_ABI_OR_GPU_ACCEPTANCE_LOCAL_ONLY_EXPORTS_UNVERIFIED`
——它自己写明了边界：静态、非 loader、非 ABI、非 GPU 验收，且 NVAccel 的 34 个符号只有局部定义（导出未验证）。

`kext_load=NO_GO`、`gpu=NOT_RUN`、`signing=NOT_RUN` 不变。

### 这个通过的边界（必须一起读）

1. 删掉的是**声明**，依据是 15.7.9 的 KC 里这 7 个名字没有可观察定义；如果我们判断错了，
   vtable 槽位会与真实类不一致。这一点只能用真机加载验证，当前没有验证。
2. 34 个 local-only 导入仍然只有「镜像里存在局部定义」的证据，导出状态未验证。
3. 三个 bundle 只是 runner 临时目录里的 MH_KEXT_BUNDLE，未签名、未装入 KC、未加载、未执行。

## 反解结论：方案 1 被推翻，虚函数应当保留（2026-10-21 晚）

内核集合反解成功，得到 `IOAccelSurface` 的真实 vtable（`research/stock-v243-offscreen-20261021/iogfx-vtable-20261021.json`，
共 120 个可命名槽位）。关键区间：

| 槽位 | 符号 |
|---|---|
| 315 | `update_shape` |
| 316 | `prune_buffers` |
| 317 | `reset_req_bits` |
| 318 | `set_scaling` |
| 319 | `add_context_to_list` |
| 320 | `remove_context_from_list` |
| 321 | `set_id_mode` |
| 322 | `set_shape` |
| **323** | **`set_shape_backing_length_ext`** |
| **324** | **`surface_lock_options`** |
| **325** | **`surface_unlock_options`** |
| 326 | `surface_control_with_lock` |

也就是说：**这 7 个方法在 macOS 15.7.9 的类布局里是存在的**，顺序与仓库重建的
`iofam/IOAccelSurface.h` 完全一致。之前静态审计把它们判成"缺失"，是因为内核集合把局部符号名
剥掉了——函数在、vtable 槽在，只是 nlist 里没有名字。

因此：

- `iofam-macos15-layout.patch`（把 7 个声明包进 `NM_TAHOE`）是**错误假设**，已停止应用；
  删掉声明会让 323-326 的槽位整体前移，`surface_control_with_lock` 会落到 323，属于 ABI 破坏。
- 正确的做法是把 **vtable 槽位证据**接进导入审计：对名字被剥掉、但槽位被观察到的符号，
  记为 `VTABLE_SLOT_OBSERVED_LOCAL_NAME_STRIPPED`，而不是 `UNRESOLVED`，更不是删代码。
- `kextutil -n` 之前在"删除后"通过，只说明没有未解析导入，不能证明布局正确；这个反例说明
  "没有未解析"与"布局正确"是两件事。
