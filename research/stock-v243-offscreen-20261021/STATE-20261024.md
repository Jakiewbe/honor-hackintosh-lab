## 5. 为什么清了守卫就开始自动重启（机制）

```
开机会员：launchd → 内核匹配 PCI 10de:25a9 → NVRM::probe()
                                                  │
        ┌─────────────────────────────────────────┘
        │  守卫在时：nvrm_driver_off() → return NULL（静默，什么都不做，机器正常）
        │  守卫清了：往下走 → NVRM::start() → RM 初始化 → 读固件（现在有了！）
        │                                                    │
        │                                    GSP 启动 → FSP 启动
        │                                                    │
        └────────────────────────────────────────────────────┘
                                        上游已知 bug：610-fsp-timer-double-destroy
                                        kfspCleanupBootState 在失败路径和
                                        kfspStateDestroy 里各跑一次 → 第二次
                                        tmrEventDestroy 踩到已释放的 timer
                                        → page fault → panic → 立即重启 → 再来一遍
```

**所以"自动重启"不是系统坏了，是我们把下一关的失败暴露出来了。** 而且这条路必须走一次，否则永远不知道卡在哪。

## 6. 现在唯一的悬念

清掉守卫之后，固件终于被读，然后三种可能：

| 可能 | 现象 | 说明 |
|---|---|---|
| **A. panic 循环** | 每次开机几秒/几十秒就重启，`*.panic` 有文件 | 最可能。就是上面那个 FSP bug |
| B. RM 起来但 adapter 失败 | 能进桌面，日志里 `RmInitAdapter failed` | 固件格式/版本不对 |
| C. 一路到 head | 日志里 `headwatch: done` 且不 STOPPED | 意外的好结果 |

**只有 panic 文件能区分 A。**

## 7. 接下来的顺序（一步一个判据）

### 第 1 步：止损 —— 让机器稳定

```bash
bash "/Volumes/UNPLUGGED 1/G1-急救.command"
```

进不去系统时：**开机按住 Shift 进安全模式**（不加载第三方 kext），再跑上面那条。
最差情况从 Recovery（`Cmd+R`）里：`sudo nvram nullmoth-remove=1`。

- 它做什么：写 NVRAM `nullmoth-remove`（驱动见此属性就 `return NULL`，完全不碰 GPU）+ 拆掉自动实验 daemon + 清守卫 + 收集 panic。
- 判据：**连续两次开机不再自动重启。**

### 第 2 步：取证 —— 把崩在哪里看清楚

```bash
bash "/Volumes/UNPLUGGED 1/G1-急救.command" panics
```

- 判据：拿到 `*.panic` 里的 `panic(cpu…` 和后面的调用栈。
- 看栈里有没有 `kfsp`、`tmrEventDestroy`、`nv_destroy_nano_timer`。

### 第 3 步：按栈修 —— 一次只改一个变量

- 若栈指向 FSP timer → 打上游 `610-fsp-timer-double-destroy.patch`，重编 NVRM，再来。
- 若是别的地方 → 按栈改，不猜。
