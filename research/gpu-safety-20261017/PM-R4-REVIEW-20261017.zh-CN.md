## P0-A：PM user busy 后仍进入 Standby

固定 NullMoth [`kexts/NVRM/NVRM.cpp`](https://github.com/nullmoth/nvidia-macos-driver/blob/ac55984c473e746c2a8ebea7ba0913461aa7c393/kexts/NVRM/NVRM.cpp)：
- `nv_xnu_pm_enter / exit` 按 `gNvPmGate` 统计活跃 RM users；R4 将 PM owner 校验移入锁内，并在启用 PM 时于 NVRM start 前置分配 gate。
- `nv_xnu_pm_close(waitMs)` 返回超时后剩余 users 数；R4 缺门禁返回 `-1`。
- `setPowerState(0)` → `gpuSuspend` → `nvkms_xnu_suspend` → `nv_xnu_pm_close(10000)`。当前 `if (busy)` 只记录日志，随后**无条件**调用 `rm_stop_user_channels`、`pciSaveForSleep`、`rm_power_management(NV_PM_ACTION_STANDBY)`，而且前一项 `rm_stop_user_channels` 失败也没有阻断后续 Standby。
- `setPowerState` 无条件 `kIOPMAckImplied`，`gpuResume` 假定先前 `fGpuPm=kGpuPmSuspended` 且 RM 真正执行过 standby。

**确认的源码缺陷：** 活跃 RM users 非零/门禁缺失时仍执行 Standby。**尚未证明：** 该分支在目标 macOS 15 物理 RTX 2050 上发生过。直接添加 `if (busy) return` 无法保证 XNU 不再给 PCI 断电，且留下 `NVKMS=SUSPENDED` 和错误唤醒前提。必须先核对 macOS 15 `setPowerState` ACK/拒绝语义，设计预静默、放弃睡眠或有根据的醒后恢复状态机，才可实施新候选。

## P0-B：KAPI Device close 失败传播缺失

固定 OGKM [`src/nvidia-modeset/kapi/src/nvkms-kapi.c`](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/e4a5faa2567f28c8eabe0ebb6422b6d0abcf37eb/src/nvidia-modeset/kapi/src/nvkms-kapi.c)：
- `KmsFreeDevice`（约 420–455 行）先尝试 `NVKMS_IOCTL_FREE_DEVICE`，然后调用 `nvkms_close_from_kapi(device->pKmsOpen)`，无论其真实结果都将 `pKmsOpen=NULL`；
- `FreeDevice`（约 625 行，返回 `void`）继续 `KmsFreeDevice`、`RmFreeDevice`、`nvkms_close_gpu`、`nvkms_sema_free`、`nvKmsKapiFree(device)`；
- 固定 NullMoth [`kexts/NVRM/os-nvkms-xnu.cpp`](https://github.com/nullmoth/nvidia-macos-driver/blob/ac55984c473e746c2a8ebea7ba0913461aa7c393/kexts/NVRM/os-nvkms-xnu.cpp) 的 R2 `kms_close_common`：`thread_call_free(eventCall)` 失败时**保留 per-open 并提前返回**；但供 OGKM 调用的 `nvkms_close_from_kapi` 依旧是 `void`。
- R4 新增的 `nvkms_xnu_try_close_bridge` 明确仅支持 `device==NULL`、`eventCall==NULL` 的 kernel bridge，不能用于 KAPI Device。

**条件性风险：** 有 KAPI worker 的 close 失败后，per-open 仍保留 `device` 指针，OGKM 却可能释放该 Device，导致潜在悬空回调/无法重试。不能把此源码可达分支当成已经发生的 GPU UAF 实机故障。最低安全修复边界涉及 `kms_close_common` / `nvkms_close_from_kapi` / OGKM `KmsFreeDevice/FreeDevice` 的失败可观察合同、唯一 owner、worker+event callback 排空、关闭次序和失败时保留资源。固定 ABI 尚为 `void`，不能凭猜测直接改变并声称链接安全。

## P0-C：NV UserClient 裸引用

[`NVRM.cpp::nv_xnu_lookup_fd`](https://github.com/nullmoth/nvidia-macos-driver/blob/ac55984c473e746c2a8ebea7ba0913461aa7c393/kexts/NVRM/NVRM.cpp)（原约 315 行）遍历 `gNvClients` 后解锁，返回 `&c->fNvfp` 和 `c`；无 retain 或会话锁跨越后续 RM 使用。其伴随函数 `nv_xnu_mmap_context` 也返回内嵌 `fMmap` 的裸指针，`os-xnu2.cpp` 包含消费此接口的路径。R4 `externalMethod/clientMemoryForType/clientClose` 串行化并不构成 lookup 外部消费者的引用保持证明。实现前须枚举所有入口及调用上下文，设计可配对 release 的 retain / 引用计数并验证锁序，不可仅延长局部锁至可能睡眠的 RM 路径。

## 本轮构建诊断增量与测试边界

`scripts/gpu-safety-r4/native_compile.py` 在原有严格 `-Werror` 与单类 `-Wno-error=deprecated-declarations` 基础上，添加 C++ 编译诊断 `-ferror-limit=100`，并在失败对象的 `native-report.json` 中保存最多 20 项 `first_errors`（完整文本仍归档）。未改变驱动源码、警告策略、x86_64/Xcode/SDK pin、KAPI C profile 或补丁顺序。Linux Clang 对包含 28 个独立未知类型错误的 C++ 样本：默认仅报告 20 项，`-ferror-limit=100` 报告全部 28 项。**该单元验证只核查编译器诊断参数，不是 macOS 原生对象编译通过。**
